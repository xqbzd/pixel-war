# 部件建模闭环（v1）

目标：让「AI 生成 + 人精修」的部件建模有一个可跑、可验证的闭环，而不是先攒一堆工具。

## 闭环长什么样

```
data/parts/*.part.txt                  ← AI 和人改的都是这里（纯文本，可 diff、可 review）
        │
        ▼  PartDef.build_volume()
   16^3 体素体积（解析式形状 + 主体色/棱色）
        │
        ├── render = texture ─→ 六面 16x16 图集 + 每单元每面 1 个四边形
        │                       （立方体部件走这条：面数固定，贴图/网格可被大量实例共享）
        │
        └── render = voxel   ─→ 贪心网格化 + 顶点色
                                （斜切等非立方体部件走这条：斜面保留体素台阶）
        │
        ├── scenes/part_preview.tscn   预览（T 切换立方体部件的路线，E 导出）
        └── exports/*.vox.txt + *.png  交给 Goxel / MagicaVoxel 继续手工精修
```

关键设计：**两条渲染路线读同一份体素体积**。所以「贴图版立方体」和「体素版棱柱」
不可能配色跑偏 —— 它们是同一份数据的两种投影，而不是两套美术资源。

## 部件文件格式

`key = value`，`#` 开始的行是注释，行尾 ` # ...` 也是注释（颜色可以写 `c9c9ce` 或 `#c9c9ce`）。

| 键 | 说明 |
| --- | --- |
| `name` | 显示名 |
| `category` | 零件菜单里的分页：`结构` / `行驶` / `武器` / `辅助` / `特殊`（英文键 `structure` / `mobility` / `weapon` / `utility` / `special` 也认）。不写 = 结构 |
| `shape` | `cube` / `half_prism_xz` / `half_prism_xy` / `half_prism_yz` |
| `cubes` | 部件占地，单位 = cube（每个 cube = 16^3 体素）。`1 1 1` = 单 cube |
| `render` | `texture`（六面贴图）或 `voxel`（体素网格） |
| `body` | 主体色，十六进制 |
| `edge` | 棱色，十六进制 |
| `edge_band` | 棱的厚度，单位 = 体素（1 = 1/16 cube） |

约束：`texture` 路线要求每个占用的 cube 都是实心 16^3，否则自动退回 `voxel` 并记一条警告
（`tests/test_vox_core.gd` 里有断言）。`half_prism_*` 的 `cubes` 截面必须是正方形。

### 约定：一个零件 = 一个建模文件（2026-10-15 起）

**除非特别说明，一个零件只对应一个 `.vox`。** 需要多个部件（轮子的轮轴 + 轮体、机枪的
底座 + 支架 + 枪管）就画在**同一个 .vox 场景的不同物体**里，部件文件里用**子模型序号**引用：

| 键 | 用途 | 例 |
| --- | --- | --- |
| `wheel_body_model = <序号>` | 轮子的轮体（轮胎）是第几个子模型，**0 号永远是轮轴本体** | 玩具轮胎 `1`、小货车轮胎 `1` |
| `weapon_yaw_model` / `weapon_pitch_model` | 转塔的支架 / 枪管是第几个子模型 | 两种机枪都是 `1` / `2` |

* 判断"是不是轮子"一律问 `PartDef.is_wheel()`（= 写了 `wheel_body_model`），别去翻模型路径。
* 老写法 `wheel_body = <另一个 .vox 的路径>`（轮轴、轮体各一个文件）**已弃用**：写了会留一条
  指路的警告，但不再生效。要恢复它得先改 `PartDef.sub_model_volume()`。
* 好处是**位置由画布决定**：两个物体在 MagicaVoxel 里怎么摆，进游戏就怎么装配
  （和武器的底座/支架/枪管一个道理），不用手写偏移。

轮子的位置换算（`PartDef.sub_model_offset()`，单位 = cube）：

```
轮体本地原点 = 画布里 (轮体原点 − 轮轴原点) + model_offset + wheel_offset
```

* 前两项是"照抄画布"：轮轴自己会被 `model_offset` 整体挪（比如玩具轮胎下移 3 象素），
  轮体跟着一起挪，所以两个子模型永远是一套装配体；
* `wheel_offset` 只是**微调**（默认 0）：画布位置不合适、又不想动模型时才写。
* 轮体**绕自己的几何中心转**（`local_centre` 来自 `tight_bounds`），所以轮心要落在轮轴轴线上
  才不会"绕着轮轴画圈"。写模型时把两个物体的中心对齐即可：
  玩具轮胎的轮心比轮轴中心低 6.5 体素（作者的选择），小货车轮胎两个中心完全重合。

断言：`tests/test_part_categories.gd` 的两条轮子测试（含"不写 `wheel_offset` 也对"的回归）
和 `tests/test_model_import.gd` 的 `test_wheel_body_is_a_sub_model_with_collision`。

### 同源武器：单连装 / 双联装

双联装机枪（`data/parts/lightmachinegunx2/light_mg_x2.part.txt`）**不新增任何代码**：
它的 `.vox` 里三个物体和单连装一一对应（底座 / 支架 / 双枪管，序号和包围盒都对齐），
所以 `weapon_*` 的字段照抄，转轴 / 转点 / 枪口由模型推导出来也逐个相同，只有数值不同
（射速 ×1.5、每发伤害略降、更重更费电、炮塔转得更慢）。
断言：`tests/test_weapon.gd` 的 `test_twin_mg_reuses_the_single_turret_geometry`
—— 它同时钉住"两把枪的推导结果一致"，防止以后换模型时对不上。

## 形状与「棱」的规则

形状是**解析式**定义的（不是逐格手绘），每个形状 = 一个 2D 截面沿某轴挤出。
这解决了一个陷阱：45° 斜面在体素里是台阶，局部邻域和 90° 拐角完全一样，
任何纯邻域规则都会把整个斜面涂成棱色。所以形状显式给出两件事：

* `occupancy` —— 哪些体素实心（斜面自然是台阶，保留像素味）
* `crease` —— 哪些体素落在真正的棱上（面与面相交处）

因此棱柱的配色是：三条长棱 + 两端封口面的轮廓是棱色，斜面本身是主体色。
立方体是 12 条棱（176 个体素，占 4.3%），在贴图版里表现为每个面一圈 1 像素的边框。

加新形状 = 在 `voxel/vox_shapes.gd` 的 `default_layout()` 加一个条目 + 写下截面谓词和棱谓词。

## 两条路线的成本（实测）

在 `part_preview.tscn` 里实测（152 个立方体部件 + 5 个斜切部件，同一台机器同一帧率条件下）：

| 立方体部件的路线 | 每个部件的 mesh | 152 个实例的三角形 | 整帧三角形 | 说明 |
| --- | --- | --- | --- | --- |
| texture | 6 quad / 12 tri + 1 张 96x16 图集 | 1824 | 约 11.6k | 面数与像素细节无关，实例再多也不涨 |
| voxel | 30 quad / 60 tri | 9120 | 约 44.1k | 同样形状走体素网格，每个部件贵 5 倍 |

斜切三棱柱（体素路线）= 156 quad / 312 tri。整帧数字（11.6k → 44.1k，+280%）比单个部件的 5 倍
更陡，因为整帧统计还包含方向光的阴影 pass（多级级联会重复画几何）。
**要比较就看单个部件的 mesh 三角形数**，这也是 HUD 里显示的那两个数。

两条路线在画面上的覆盖率一致（帧缓冲里灰色像素约 5.7k，切换路线后基本不变），
所以差别纯粹是成本，不是外形。

实测方法（可复现）：

1. 编辑器里打开 `scenes/part_preview.tscn`，F5 运行。
2. `T` 切换立方体部件的路线，HUD 里的 `tri/部件` 与整帧数字同时变化。
3. 用 MCP 的话更直接：`editor_manage(op="game_eval")` 调 `PartPreview.route_stats()`。

## 坐标与单位

* 1 cube = 1 世界单位 = 16x16x16 体素 → 体素边长 1/16。
* 部件本地空间 = `[0, cubes]`，体素索引 `(x, y, z)`，`y` 向上。
* `VoxMesher` 的每个朝向表满足 `u x v = n`（让朝向判定确定且可验证），但发顶点时**反序**成
  `p0,p2,p1 / p0,p3,p2` —— 因为 Godot 的正面是顺时针（见下面第 5 条坑）。
* 导出到 Goxel/MagicaVoxel 时按 Z-up 换轴：`gx = x, gy = size.z-1-z, gz = y`。

## 常见坑

1. **导出时数据文件会丢**：`*.part.txt` 是非资源文件，导出预设里要把
   `*.part.txt` 加进「Filters to export non-resource files」。
2. **不要用逐体素画内部**：实心 16^3 有 1536 个外表面、内部更多；贪心合并 + 只画暴露面
   是底线（`voxel/vox_mesher.gd`）。
3. **贴图模式别用在非立方体上**：会静默退回体素路线并给警告，别指望它自动变好看。
4. **损伤粒度 ≠ 体素粒度**：cube 才是伤害/建造单位，16^3 只是外观。
   现在这套数据结构（体素体积 + cube 单元）已经把这个分界留下了。
5. **环绕方向：Godot 的正面是顺时针**（这个坑已经踩过一次）。按“逆时针朝外”发顶点时，
   背面剔除会剔掉朝向相机的面，于是你看到的是**被它挡住的里面的背面** ——
   表现就是“朝向我的那面没渲染，反而渲染了背后的部分”，而且不报任何异常。
   判定办法写进了测试：拿 Godot 自带的 `BoxMesh`（一定正确）反推引擎约定，
   实测 `engine = -1`（几何法线与外法线反向），再要求自己的网格同号。
   改动任何网格生成代码后，先跑 `test_mesh_winding_matches_engine_front_face`。
6. **色彩空间：顶点色要自己换算成线性**（这个坑也踩过一次）。同一个 `c9c9ce`，
   贴图路线的值存在 sRGB 纹理里、由 GPU 解码成线性；顶点色写进 `COLOR` 数组后
   Godot **直接当线性值**用。不换算的话，体素部件（棱柱）会比贴图部件（cube）白一档 ——
   实测差值：贴图 `0.886`、顶点色原样 `0.953`、换算后 `0.886`（与贴图逐位一致）。
   所以顶点色统一走 `VoxVolume.linear_color_of()`，而图集 PNG 导出仍写 sRGB，
   保证外部工具打开时看到的是你写的那个色号。守护断言见
   `test_voxel_vertex_colours_are_linear_to_match_texture`。
   注意顶点色在网格里是 **8 位存贮**，所以换算后会有一位量化误差：生产代码实测两条路线
    的同一个面为 `0.9373` vs `0.9333`（单通道 0.4%），肉眼不可见；要完全一致只能统一走贴图，
    或让图集也量化到同样的值。

## 载具与主界面

主界面 = [scenes/main_menu.tscn](scenes/main_menu.tscn)（已设为项目主场景，编辑器里 F5 直接进）。

* **主体**：`VehicleViewer`（`scripts/vehicle_viewer.gd`）跑在 SubViewport 里，**只转视角**：
  地板和载具完全静止，相机绕着载具自动环绕（16 度/秒）+ 左键拖拽 + 滚轮缩放；
  相机按载具包围盒自动取景（实测：侦查艇 5x2x2 → 10.42、运输舰 6x2x5 → 14.62、
  塔台 2x7x2 → 13.69，与 `半径 / tan(fov/2) * 1.32` 逐位吻合）。
  ⚠️ **贴地要用"真实包围盒"`VehicleDef.actual_bounds()`，不是 `bounds()`**：
  `bounds()` 用的是**声明的 cubes 盒子**，而轮体（轮胎）是挂在盒子外面的**附属子模型**
  —— 拿声明盒算"车底"会算高一截，半个轮胎插进地板（用户报的"预览时半个轮胎卡在地里"）。
  实测用户那台车两者差 **1.000 格**（= 20 厘米），正好是半个轮胎。
  `actual_bounds()` 用每个零件的网格包围盒（`mesh_bounds()`，含轮体、含 `model_offset` 的下探），
  所以拿它抬完，最低点正好落在 y = 0。**出生点同理**（见 `TestField._chassis_spawn_point()`：
  把"最低点"抬到地面上方 `SPAWN_HEIGHT`，而不是把底盘原点摆上去）。断言：
  `test_actual_bounds_catches_the_wheels_below_the_declared_box`（含"没有轮子的车两者应当一致"
  这条防改过头）；实测进游戏落地后轮胎底面与地形差 **0.000 格**、8/8 轮着地。
* **建造场地**：`VehicleViewer.BUILD_AREA_CUBES = 64 x 64 x 64`。地板固定在 y = 0，
  一张贴图铺满 64 x 64 cube（1 个 draw call）：瓦片是 16 x 16 texel（一格 = 1 cube = 16 texel，
  与部件自身的体素密度一致），灰底 `585c66` + 上/左各 1 texel 灰蓝格线 `7488a8`，
  靠 `texture_repeat` + `uv1_scale = 64` 平铺，`NEAREST_WITH_MIPMAPS` 让近处锐利远处不闪。
  载具贴地站住（x/z 居中、车底落在 y = 0），所以切换载具时地板和视角都不动。
  用「小瓦片 + 重复」而不是烘一张 1024 x 1024 的整场贴图：1 KB 对 4 MB，改场地尺寸也不用换贴图；
  将来要按格子做独立标记（区域、禁放区）时换成烘焙整场贴图即可，材质接口不变。
* **光照：全向柔光**（建造界面和载具预览共用）。主光是天空 IBL —— `make_garage_sky()` /
  `make_garage_environment()`：`ambient_light_source = AMBIENT_SOURCE_SKY`，天空刻意接近中性灰
  （太蓝会把地板和部件一起染色，埋掉"灰底 + 灰蓝格线"的区分度）。方向光只剩很弱的
  `SUN_ENERGY = 0.25`，`light_angular_distance = 6°` 拉开半影，`sky_mode = LIGHT_ONLY`
  避免往天空里画太阳盘（否则 IBL 里出现热点，光又变"有方向"了）；它的作用只是给地板留一圈软接触阴影。
  实测同一材质的各朝向亮度（后期色调映射后的值）：

  | 朝向 | 改前（方向光 1.15 + 固定环境光） | 改后（天空 IBL + 弱方向光） |
  | --- | --- | --- |
  | +Y 顶面 | 0.763 | 0.625 |
  | -X / +Z（受光侧） | 0.681 / 0.716 | 0.484 / 0.456 |
  | +X / -Z（背光侧） | 0.386 / 0.386 | 0.385 / 0.385 |
  | 四个水平朝向的相对起伏 | 61% | **23%** |
  | 顶面相对水平面 | +41% | +46% |

  也就是说：棱柱台阶（都是水平朝向的面）的明暗条纹被压掉一大半，而"顶面更亮"的形体感还在。
  守护断言：`test_garage_lighting_is_omnidirectional_and_soft`。
  开发用的 `part_preview` 共用同一套光：`scripts/part_preview.gd` 直接调
  `VehicleViewer.make_garage_environment()` / `make_garage_sun()`，地面也换成同一块格线地板
  （`make_floor_material(Vector2(60, 40))`，一格 = 1 cube，顺手当比例尺用）。
  两个场景实测的同一材质各朝向亮度一致（差 ≤0.03，来自观察角度不同带来的高光差异）。
* **顶栏**（从左到右，严格按需求）：游戏设置 / 部件百科 / 进入战斗 / 进入载具编辑 / 读取载具列表。
  前三项 + 载具编辑 = 占位页（`main_menu.gd` 里的 `PANELS`，换成真页面时替换它）；
  读取载具列表 = 下拉栏，列出 `data/vehicles/*.vehicle.txt` 并给当前项打勾，选中即切换预览。
* **载具格式**（`data/vehicles/*.vehicle.txt`）：

      name = 侦查艇 / Scout
      part = cube_full 0 0 0 0      # 部件id x y z yaw(度)

  单位是 cube；y 向上、-z 为车头方向；yaw 只支持 90 度一档（非倍数会吸附并告警）；
  同一格放两个部件会被 `overlap_cells()` 报出来，`tests/test_vehicle.gd` 守着这条。
  **保存时坐标原样写、不做归一化**：载具在场地里的位置要一格不差地还原。
  曾经归一化到最小角 `0,0,0` —— 结果带轮子的车一存一读，轮子被压到最底排，
  而轮轴下探 3 像素 → 加载时判定超框、整排被跳过（用户报的"保存退出后车贴地、轮子没了"）。
  加载时只在**必要时**整体挪最小的量把载具塞进场地（`BuildGrid.fit_shift()`），
  并且会提示"载具整体上移 N 格"/"有 N 个零件放不下" —— 绝不静默丢零件。
  断言：`test_wheel_vehicle_survives_floor_shift_on_load` / `test_save_reload_round_trip`。
* **共用设施**：`PartLibrary`（`voxel/part_library.gd`）统一负责扫描部件、按 (部件, 渲染路线)
  缓存构建结果、打包 MultiMesh。主界面、载具列表、将来的编辑器、以及开发用的 `part_preview`
  都走它 —— 同一个部件在所有场景里共享同一个 mesh + 材质。

## 建造模式（scenes/build_mode.tscn）

### 零件选择：10 格物品栏 + `Tab` 零件菜单

零件会越来越多（目标：上百种），所以**物品栏不再等于"全部零件"**，而是玩家自己配的 10 格：

| 交互 | 行为 |
| --- | --- |
| `1`..`9` / `0` | 选第 1..10 格（第 10 格挂在 `0` 上，和键盘那排一致） |
| `Tab` | 呼出 / 收起零件菜单（悬浮在屏幕中间；开着时鼠标解锁，关掉自动锁回去） |
| 菜单左侧 5 个按钮 | 结构 / 行驶 / 武器 / 辅助 / 特殊 —— 分页来自部件文件的 `category` |
| 菜单右区 | 这一类的零件，**正方形斜向视图 + 名字**，多了能滚 |
| 拖 菜单 → 某格 | 放进那一格（原来那格被替换） |
| 拖 某格 → 另一格 | 两格**互换位置**（不是插入） |
| 拖 某格 → 菜单区域 | **清空**那一格（空 = 建造枪手上没东西，左键会提示"这一格是空的"） |
| 左键点菜单里的零件 | 放进**当前选中格**（懒得拖的时候用） |
| 中键点场上的零件 | 见下面那条规则 |

中键拾取（用户定的三条，顺序不能变）：

1. 物品栏里**已经有**这个零件 → 跳到那一格；
2. 没有、但**有空格** → 放进第一个空格并跳过去；
3. 没有、且**全满** → 替换**当前选中**那一格。

分工（改这块时别把三层搅在一起）：

* `voxel/part_loadout.gd` —— 10 格 + 上面那三条规则，**纯逻辑、不碰 UI**，被
  `tests/test_part_loadout.gd` 逐条守着（中键的三条分支都在里面）；
* `scripts/part_picker.gd` —— 只负责画（物品栏 / 菜单 / 拖拽预览）和把鼠标事件翻译成
  `PartLoadout` 的调用，对外只发 `slot_selected` / `slot_changed` / `menu_toggled` / `notify`；
* `scripts/build_mode.gd` —— 接信号：重刷手上的模型、虚影、HUD；它不再自己数零件。

**拖拽是自己实现的**，没用引擎的 `_get_drag_data` / `_can_drop_data`：引擎那套只认
"鼠标底下那个控件肯不肯接"，而"拖回菜单区域就清空"要求整块菜单（含遮罩）都算落点，
用它反而要到处贴 `_can_drop_data`。自己实现只有三个判断：落在哪个格子 / 落在菜单区域 /
都不在（= 取消）。按下后移动不到 6 px 当点击处理（点格子选格、点菜单项放零件）。

### 零件图标（斜向视图）

`voxel/part_icon.gd` 用**纯 CPU** 把体素体积画成 2:1 的斜向视图（顶面菱形 + 前面 + 右面，
三档明暗 `1.0 / 0.8 / 0.6`），本体和轮体的体素都算进去。

* 不每个零件开一个 `SubViewport`：上百个零件就是上百个渲染目标，而且每个都要等一帧才能截图；
* 按需生成 + 缓存：`PartLibrary.icon(id)` 第一次用到才画，之后返回同一张 `ImageTexture`
  —— 菜单只建**当前分类页**的零件项，没打开过的分类一个像素都不画；
* 投影尺寸随零件大小走（`65x65` / `139x123` …），最后**等比**缩进 64x64 的方格：
  图标之间的大小关系要能比（玩具轮胎就该比小货车轮胎小一圈）；
* 画出来的几何 = 同一份体素数据，所以图标不可能和实物跑偏。

要看图标长什么样（无头也行，会把形状打成字符画并导出 PNG）：

```
godot --headless --path . --script res://tools/probe_icons.gd
```

断言：`tests/test_part_icons.gd`（正方形 / 透明四角 / 三档明暗 / 轮体算进去 / 缓存）
和 `tests/test_part_picker.gd`（10 格、分类页、点击落位）。分类本身的数据守门在
`tests/test_part_categories.gd`。

### 外部建模工具接入（推荐路线）

**不要用 AI 手写形状** —— 用现成的体素工具建模，游戏这边只做导入：

1. 在 **Goxel**（开源，带脚本/命令行）或 **MagicaVoxel**（免费，生态最大）里画，
   也可以在 **Blender** 里体素化后导出；
2. 存成 **Goxel 纯文本体素格式**（每行 `x y z rrggbb`）。这个格式和游戏导出的
   `exports/*.vox.txt` 是同一个（对照过 Goxel 源码 `src/formats/txt.c`），
   MagicaVoxel 的 `.vox` 可以在 Goxel 里打开后另存为 txt；
3. 把文件丢进 `data/parts/models/`；
4. 打开 **部件实验室** `scenes/part_lab.tscn`（F6 直接跑）：
   - 自动转着看模型，**文件一改就重载**（每 0.4 秒查一次修改时间）；
   - 连接面自动推导并标出来：绿色 = 可连接面，黄色 = 默认连接面（最朝下的那个）；
   - `1..9` 选模型、`R` 暂停自转、`G` 在 `data/parts/` 生成/更新对应的 `.part.txt`、
     `E` 另存一份体素文本到 `exports/`；
5. 生成出来的部件立刻出现在建造模式的零件菜单里（按 `order` 字段排；`Tab` 打开菜单，
   分类那一页由部件文件里的 `category` 决定）。

部件文件里新增两个键：

| 键 | 说明 |
| --- | --- |
| `model` | 体素模型文件路径；设了它就用模型，`shape` 不再参与 |
| `connections` | 可选，手动指定连接面（如 `+z -z`）；不写就自动推导 |

自动推导的判据：某方向**最外侧那一层**露出的格数 ≥ 100（约 40%）就算连接面。
这条判据对形状库里的解析形状和外部模型用的是同一套（测试里逐形状验证）。
模型缺失时不会崩，会退回用 `shape` 并留一条警告。

入口：主界面「进入载具编辑」。出生点在场地前方（+x 方向、车头朝 +x），
地板是同一块 64 x 64 格线地板，正前方有琥珀色方向箭头。

操作：`WASD` 平移、`空格` 升、`Shift` 降、鼠标转向、`滚轮 / R` 旋转部件、
`Tab` 打开零件菜单、`1`..`0` 选物品栏（底部 10 格高亮）、`左键` 建造、`右键` 拆除、
`中键` 点零件 = 收进物品栏（规则见上面「零件选择」一节）、
`M` 开关镜像建造（`【` / `】` 挪对称面）、
`ESC` 打开菜单（继续建造 / 游戏设置 / 保存 / 去测试场 / 退出）。

整辆载具的平移（不改变形状，只挪位置）：

| 按键 | 效果 |
| --- | --- |
| 小键盘 `8` / `2` | 沿 `+x` / `-x` 移动（`+x` 是车头方向） |
| 小键盘 `4` / `6` | 沿 `-z` / `+z` 移动 |
| `<`（即 `,`） | 整体下降 1 格 |
| `>`（即 `.`） | 整体上升 1 格 |

平移是**先整体校验、再整体搬**：任何一块会超出 64 x 64 x 64 场地就整体拒绝（格子、变换、
连接账本都不动），并在 HUD 上提示原因。断言：`test_translate_all_is_all_or_nothing`。
按住方向键会以约 110ms 的间隔连发（自己节流，比键盘 echo 稳）。

### 镜像建造（左右对称）

`M` 开关镜像建造，`【` / `】`（即 `[` `]`）把对称面左右挪**半格**，HUD 里会写出对称面
的世界坐标。对称面 = 世界 `z = mirror_half / 2`：`mirror_half` 为偶数时落在格线上
（`0` = 场地中线，正好是 `data/vehicles` 里那几辆载具的对称线），奇数时落在某一格的正中。
两种都让“整数格 → 整数格”，所以半格挪动不会把镜像体甩到格外面去
（`test_mirror_cell_is_an_involution_at_half_steps`）。

* 镜像体 = 本体**绕自己的 z 中线对折**之后再镜像。库里的零件大多左右轴对称（对折 == 自己，
  `mirror_fold_rotation()` 给出单位阵）；两个角块的对称面**不平行于坐标轴**（对角切面），
  对折之后形状变了 —— 但它们的对折结果能用**一个轴对齐旋转**复原（`x+z-y` 那种，
  在立方体 24 个旋转里搜出来的），所以照样是“同一个模型转个角度”，**不需要左手系副本**。
  镜像摆放永远是一个正常的「旋转 + 平移」（行列式 +1），存档里的 yaw/pitch/roll 能原样记下来
  （`test_mirror_basis_survives_the_euler_round_trip_for_every_part` 逐零件验）。
  ⚠️ 对折旋转是**绕盒子中心**转的，所以公式里有一项平移 `a = 盒子中心 - A·(盒子中心)`；
  漏掉它镜像体就整体偏一格（角块那种非单位阵才会暴露，轴对称零件 a = 0 看不出来）。
  断言：`test_mirrored_placement_equals_true_reflection_voxel_by_voxel`（逐体素跟真镜像比，
  本体 + 轮体一起算，6 个零件全过）、`test_mirror_placement_stays_a_normal_grid_placement`
  （朝向必须是纯旋转、坐落在 1/16 格上、`(cell, basis)` 和 `transform` 自洽、
  足迹格子逐格镜像）、`test_mirror_fold_rotation_of_every_part`。
* **本体和镜像体各自过一遍完整检查，而且互相独立**（用户要求）：越界 / 体素级干涉 /
  部件点数预算。**谁过不了检查就不放谁，另一边照放** —— 比如镜像位置被占/超框，
  本体照样落；本体撞着东西，镜像体照样落。放不下的那一边画红色虚影 + HUD 写原因。
  * 镜像体的检查里只有"本体真的要落子"时才把本体算进去（算进干涉和点数预算），
    本体自己都放不下时不该拖累镜像体；
  * **点数只够一件时：只放本体**（本体先算，镜像体再查时点数已经记在本体头上了）。
  * 断言：`test_mirror_places_only_the_body_when_the_mirror_side_is_blocked`、
    `test_mirror_places_only_the_body_when_the_mirror_copy_leaves_the_arena`、
    `test_mirror_places_only_the_mirror_when_the_body_is_blocked`、
    `test_mirror_prefers_the_body_when_points_only_fit_one`、
    `test_can_place_counts_extra_parts_in_the_clash_check`（干涉 + 点数都要连 extra 一起算）。
* 零件正好骑在对称面上（`mirror_half` 为奇数、零件就在那一格）时，镜像 == 本体，
  只放一个就够 —— 这时候本来就对称，不该报“和自己撞上了”
  （`test_mirror_plan_places_once_when_the_part_sits_on_the_plane`）。
* `右键`拆除也镜像：本体 + **镜像位置的基准格**上那个零件一起拆（`remove_with_mirror()`）。
  **不记"谁是谁的镜像"，也不反推镜像摆放**：基准格直接按格子镜像（`mirror_cell()`），
  谁站在那一格就是谁。这条成立的前提正是"锚点绑在本地格子上"：镜像体用的是同一个本地格子，
  镜像又把格子映到格子，所以镜像体的锚点正好是本体锚点的镜像格。
  断言：`test_anchor_mirrors_to_the_mirrored_part`（6 个零件 × 24 个旋转 × 3 个半格档位）/
  `test_mirror_delete_pairs_by_mirrored_anchor_cell`。
  镜像位置没有对应零件时只拆本体（`test_mirror_delete_removes_only_the_body_when_unpaired`）。
* ⚠️ **镜像性由人判断，代码不自动否决零件**（2026-10-15 用户要求）：任何零件都能镜像，
  找不到严格对折时按单位阵处理（"放得下就放"，但镜像不是逐体素的真镜像）。
  `mirror_fold_rotation()` 现在只做两件事：给两个角块找那个非单位阵的对折旋转、
  把"对不上几个格子"报在 `mismatch` 里。将来真加非对称零件 → 用户会单独说明，
  那时再按说明处理（另做左手系副本 / 在部件文件里声明），而不是让代码去猜。
  断言：`test_mirror_does_not_auto_refuse_asymmetric_parts`（拿测试里现造的手性块当样张）
  和 `test_mirrored_placement_equals_true_reflection_voxel_by_voxel`（库里 9 个零件严格 0 对不上）。
* 镜面在场地里画成一片半透明竖直面 + 地板上一条青线（只在镜像模式开着时显示）；
  镜像体的虚影偏青，和本体的白虚影一眼分得开。

### 连接点规则（实现见 voxel/part_def.gd + voxel/build_grid.gd）

* **连接面** = 形状上“平面且够大”的面。立方体 6 个；三棱柱 = 两条直角边所在的正方形面
  + 两个三角端面 = 4 个；斜切出来的台阶不算（拼不出来、贴不上）。
  判据在 `test_connection_faces_pass_the_planar_and_big_enough_rule` 里可执行验证
  （三角端面露出 136 格 ≥ 半个面；斜切台阶只有 16 格，判不合格）。
  阈值取“露出面积 ≥ 40%”而不是“半个面”：角四面体（`corner_tetra`，判据 `x+y+z ≤ 15`）
  的斜切面只有 1 格、三个半格正方形面是 136 格；切角块（`corner_cut`，取补集）的切面是
  120 格，正好卡在 40% 线上 —— 所以角四面体 3 个连接点、切角块 6 个，和预期一致。
  两个角块的朝向约定：角四面体的角点在**原点**（切面朝下，作为默认连接点）；
  切角块**反过来** —— 被切掉的角搬到**上方**，因此默认连接点是完整的正方形底面，
  而且它比四面体**少切一层**（切掉 680 格而非 816 格），所以两者不是精确互补。
* **默认连接点** = 最朝下的连接面。`half_cube` 特意做成斜坡型（底面是完整的 16 x 16 正方形），
  这样“默认连接点 = 正下方的正方形面”才成立 —— 角柱型三棱柱没有朝下的正方形面。
* **部件表只留 2 个**：立方体 + 斜坡三棱柱。原来还有一个“侧向斜坡”（`half_prism_yz`），
  但滚转已经能给出任意水平朝向，它是冗余的 —— 等价性有断言守着：
  `test_yz_ramp_is_the_xy_ramp_rotated` 逐体素 + 逐棱验证“xy 斜坡绕 Y 转 90 度 == yz 斜坡”。
  删掉它还有个副作用好处：运输舰的批次从 3 降到 2（侧向倒角与车头倒角共用同一个部件）。
* **建造永远用默认连接点去贴**：滚转档位让零件绕默认连接点所在轴转，所以默认连接点
  始终对着目标面；侧向建造时零件会**按贴合方向翻倒**，这是预期行为。
* **直接放置必须吸附在连接点上**：瞄到没有连接点的面（斜切面 / 薄边）不给候选
  （`plan()` 里判"新零件这一侧 + 目标那一侧都得是连接面"，HUD 写"该面没有连接点"）。
  ⚠️ **"悬空合法"是针对镜像体的**：镜像体跟着本体镜像过去，那边什么都没有也照样落子，
  不受连接面约束 —— 不是让直接放置去吸附没连接点的面（用户专门澄清过）。
  另外 `can_place()` 只看几何，不看连接账本：面合格就能放，账本那一对可能因为
  那一格已经被占着而记不上。能不能进测试场由 `robot_status()` 判
  （没核心 / 有零件没连上核心就进不去）。断言：
  `test_direct_placement_snaps_only_to_connection_faces` / `test_mirror_copy_may_float` /
  `test_placement_requires_free_cells_and_blocks_overlap`。
* 一个小面（`(cell, 朝向)`）最多一对连接，`links` 账本双向登记 —— 从数据层堵死“多对一”；
  已经被占着的小面**跳过不记**（不是拒绝放置）。`_collect_pairs()` 只在"两边都真的露出
  够大的面"时才登记一对。代价：极少数情况下（多个零件共用一格、又都想接同一面）
  后放的那个记不上连接，可能被判成"没连上核心" —— 悬空本来就是允许的中间状态。
* 贴地那一次也不需要连接对（地面就是基准）；范围限制 64 x 64 x 64。
* **指向判定按实际体素**：满方块走格子级快路径；非满方块在命中的格子里做 1/16 精度的
  体素步进 —— **虚空直接穿过**（三角块被斜切掉的那角不再有指向判定），
  而且命中的体素面必须落在**格子外表的平面**上才算可建造面（打到斜切台阶返回 `dir = ZERO`，
  界面提示“这面不能建造”。断言：`test_prism_void_is_not_aimable`。
* **碰撞箱按真实体素算，不按声明的 `cubes` 盒子**：`PartDef.mesh_bounds()` 取的是模型里
  实心体素的范围（`outermost_layer` 六个方向），再按 `model_offset` 平移。
  模型很少填满声明的盒子 —— 轮轴声明 `cubes = 2 2 1`（32 像素高），实际只有 19 像素高；
  以前拿盒子当包围盒，碰撞箱会凭空高出 13 像素，表现成“上面明明空着却放不下方块”。
  断言：`test_model_overhang_blocks_below_but_frees_the_top`。
* **多零件共享格子**：`cells[cell]` 是**数组**（同一格可以住多个零件），
  `parts` 是每个零件一份的 entry 列表。**能不能放只看一条**：谁都不许和别人**真的穿模** ——
  唯一的碰撞判据是体素级 `mesh_clash()`（先比包围盒，真重叠了才逐体素比对）。
  所以非满格可以共存：轮轴在自己足迹格里只有一小条体素，那一格里空着的地方就还能塞别的零件。
  **锚点（`anchor`）= 绑死在模型本地的一个格子上**，摆放时按朝向转过去。
  本地格子 = 本体 AABB **中心**所在那一格（正好压在格线上时取**下面**那一格），
  用它的**格心**当本地锚点：
  * 轮轴本体在 x 上正好 2 格厚、AABB 中心落在 x = 1 的格线上：取下面那格才是"本体最靠
    -x 的那半块"（安装板靠 -x 那半）。这条是用户按绿方块对出来的。
  * **为什么必须绑本地格子**（踩过的大坑）：以前是"摆放之后按世界坐标算一个点、再取它落在
    哪一格"——`model_offset` 把本体挪出盒子（轮轴下移 3 像素），本体相对盒子的方向跟着朝向
    转，于是同一个点有时落在本体上、有时落到本体外面（实测 24 个朝向里 12 个锚点离本体
    差 1 格）——看着就是"锚点飞了"，而且能解释好几个诡异的错位 bug。
  * 取"格心"（半整数）而不是 AABB 中心点：轴对齐旋转 + 整数格平移之后它仍落在格子正中，
    不会被"正好压在格线上"的取整扔到隔壁格去。断言：`test_anchor_always_lands_on_the_body`
    （6 个零件 × 24 个朝向，锚点必须压在本体体素上）。
  * **锚点不独占**：它只是"户口"（镜像拆除按它认零件）—— 两个零件可以共处一格，
    只要不穿模（轮轴安装板中间塞三角块就靠这一条）。早年用"基准格独占"拦过，
    结果把本来能共享的位置也拦掉了。断言：`test_anchor_is_per_part_and_sharing_is_allowed`。
  断言：`test_parts_can_share_a_cell` / `test_anchor_cell_is_exclusive_and_never_empty` /
  `test_sub_model_creates_no_anchor` / `test_anchor_check_uses_the_new_part_own_anchor`；
  另外 `tests/test_saved_vehicles.gd` 会把 `data/vehicles/*.vehicle.txt` 全load 一遍，
  保证存档里的每个零件都还放得下（规则一改，最先碎的就是存档载入）。
* **足迹盒**（`cell_box_of()` = 碰撞箱盖到的 cube 格子，向下/向上取整）现在只用来**记账**：
  连接对算在哪些小面上、射线按格查零件、整体平移、拆除。正好贴在格子边界上的面不多占一格
  （轮轴顶面正好落在 `y + 1.0`）。
* **射线在同一格里挑最近的零件**：`_raycast_part_voxels()` 会连命中距离一起返回，
  `raycast()` 在共享格子里取最近的那个 —— 拆零件 / 中键拾取都靠 `hit["part_id"]`。
* **连接小面还要"这一格真的露出面"**：`claims_face()` = 零件级有这个朝向的连接面 **且**
  `face_coverage()`（零件在**这一格**的格子外表面上露出多少格）≥ `VoxModel.MIN_CONNECTION_AREA`。
  只按"零件级连接面 + 格子"记账的话，`model_offset = 0 -3 0` 的轮轴会在**下探那一排格子**上
  凭空多出一个连接点（那一格只被模型底部薄薄一层擦到），同格里放别的零件就撞
  “一对多”——而提示完全看不出真正原因。两边的面都要满足才**登记**连接对
  （登记不上不影响放置，只是这块零件没接上）。断言：`test_axle_does_not_claim_sliver_faces`。
* **"内部面"要按几何判，不能按足迹**：一个小面算是零件自己的内部面，当且仅当
  **对面那一格上本零件自己的几何也压着它**（`face_is_internal()`）。
  拿"对面那一格在不在足迹里"去判会出事：轮体让轮轴的足迹多出一圈，于是安装板那两片
  **薄面（±z）**被当成内部面跳过 —— 那正是轮轴声明的 4 个连接点里的两个，安装板上明明
  能吸附的位置却登记不上连接。断言：`test_axle_thin_faces_are_real_connection_points`
  （对外连接点正好 4 个，且贴着薄面放方块真的登记成对）。
* **射线在体素格里的换算要带 `model_pad`**：网格原点在 `-pad/16`，所以本地坐标 `l`
  对应体积索引 `l * 16 + pad`（`_cell_base()` 同理由 pad 决定）。漏掉 pad 就会把
  下移过 3 像素的零件整体看歪 3 像素 —— 轮轴顶面会被判成“内部面”（`dir = 0`，连虚影都不给）。
  断言：`test_building_on_top_of_the_wheel_axle`。
* **反平行贴合绕世界 UP 转 180°**（而不是绕 `from × UP`）：后者会把零件顺带上下颠倒，
  带 `model_offset` 的零件在机身左右两侧就对不上了（一边下探 3 像素、一边上翻 3 像素）。
  竖直方向的反平行（挂顶棚）绕 X 轴转，只能倒过来，这是没法避免的。
* **附属子模型（轮体）**：`wheel_body_model`（轮体 = 同一个 .vox 里的第几个物体）
  + 可选的 `wheel_offset` 微调；位置默认由画布里的相对位置决定（见上面「一个零件 = 一个建模文件」）。
  它不是独立部件 —— 跟着所属零件走，**而且算碰撞体积**：
  - `sub_model_volume()` 按 .vox 自己的范围向上取整到 cube 读进来（保证两块体积落在同一个
    1/16 栅格上，逐体素比才准）；
  - `mesh_bounds()` = 本体盒 ∪ 子模型盒 → 足迹、超框判定、干涉粗筛都自动带上它；
  - `_solids_of()` 返回"本体 + 子模型"两块，`mesh_clash()` 两两比、射线也两两试
    （不然会"透过轮胎"瞄准）；
  - 但**连接点只认本体**（`face_coverage()` 只看零件自己的体积）—— 轮胎上没有连接点，
    所以轮体那几格不会凭空多出连接对；
  - 渲染：`PartLibrary.build_sub()` 出独立网格（顶点已按挂载偏移摆好），
    `make_part_nodes()` 把它和本体打包成两个 MultiMesh，共用同一批实例变换；
    独立一份是为了以后在测试场里挂到 VehicleWheel3D 上随悬挂浮动。
    **凡是画零件的地方都要画两块**：建造场地里已放下的零件（`make_part_nodes()`）、
    建造枪上悬浮的零件（`_holo` + `_holo_sub`）、瞄准的半透明虚影（`_ghost` + `_ghost_sub`）、
    主界面载具预览（`VehicleDef.instantiate()`）。漏掉任何一处都会"只剩下轮轴没有轮胎"。
  断言：`test_wheel_body_is_a_sub_model_with_collision`。

### 机器人层规则（数值 / 核心 / 点数 / 进测试场）

* **每个部件三个基本数值**（`data/parts/*.part.txt` 里手填，默认 1kg / 1000 血 / 1pp）：

      weight = 1     # 重量，kg
      hp     = 1000  # 血量
      pp     = 1     # 部件点数

  合计由 `BuildGrid.totals()` 给（带缓存，场地一变才重算），建造界面左上角就是它。
* **重心 = 零件的几何中心**：`PartDef.center_of_mass()` 取 `mesh_bounds()` 的中心。
  这个值只在第一次算（`mesh_bounds` 本来就缓存），游戏里每帧问也是 O(1)；
  想调质量分布可以在部件文件里写 `center = x y z`（单位 = 体素）覆盖。
  `tools/inspect_models.gd` 会把每个部件的数值和重心一起打出来，方便手调。
* **核心**：`data/parts/core.part.txt`，2x2x1、亮蓝主体 + 灰色棱、`core = true`。
  一台机器人**最多一个**（`can_place()` 会把第二个挡掉）；核心被摧毁 => 整机被摧毁
  （目前只有标记和唯一性，真正的摧毁判定等战斗系统）。
* **点数预算**：`BuildGrid.PP_LIMIT = 2000`。放不下的理由会写清
  “点数不够：已经用 X / 2000，这一件还要 Y pp”。
* **进测试场的前置条件**：`BuildGrid.robot_status()` —— 装了核心，而且**所有零件都和核心连通**
  （连通图走 `BuildGrid.link_pairs()`，见下面"连接图"那条）。
  返回 `{ok, reason, has_core, parts, connected, detached}`。
  **判定只在"保存 / 去测试场"时做**（2026-10-13 用户要求）：建造模式改一个零件就把结论置脏、
  HUD 显示"改动后未校验"，不再每次改动都算一遍（200+ 零件的大车白花钱）。

  或者直接告诉 AI"就用我现在这个位置"，它可以从运行中的游戏里把坐标读出来。

**缩放**：整套（含碰撞）挂在同一个 `_arena_root` 下，**改根节点缩放就是整体缩放**，
不用重建碰撞。默认 `TestField.ARENA_SCALE = 1.0`；进游戏按 `[` / `]` 现场调，HUD 上显示当前倍数
（缩放后会重新出生一次，让车落在新地面上）。
`godot --headless --path <项目目录> --script res://tools/inspect_arena.gd` 会打印各倍数下
的实际尺寸对照（房子多大 / 场地多大 / 车长 25 格），用来定倍数。
（单位是**格**：1 格 = 0.5 米，所以车长 25 格 = 12.5 米。比例是格空间里的东西，
改 `CUBE_METERS` 不会改变"车和房子谁大"。）

**已经没有用到的素材目录**（`assets/arena/racing_kit/`、`platformer_kit/`、`nature_kit/`
和 `scripts/arena_kit.gd`）是前两版留下的，可以整个删掉，不影响任何东西。

* **底盘**：普通 `RigidBody3D`（换成自定义轮胎后不再需要 `VehicleBody3D` —— 轮胎力是我们自己
  用 `apply_force` / `apply_torque` 施加的，重心会自然参与力矩，所以还得把 `can_sleep` 关掉）。
  每个零件一个 `BoxShape3D`（用**本体**包围盒，轮胎不算），质量 = 部件 `weight` 之和，
  质心 = 各零件重心按重量加权 —— 只在进场时算一次，不是每帧。
* **轮子 = 自定义"整圈 16 射线"轮胎**（`_add_wheel()` / `_apply_wheel()`，2026-10-12 换上）：
  `is_wheel()` 的部件（轮轴）→ 一个普通 `Node3D`（放在轮胎几何中心，半径取轮胎盒子 y/z
  较大者一半），轮胎网格挂它下面；物理全在 `scripts/test_field.gd` 里自己算。
  - **为什么换**：原生 `VehicleWheel3D` 每个轮子只有**一条竖直射线且不可配**，轮子骑上台阶、
    路缘、坡脚时"感觉不到"，越野很差。（早年试过"一簇 VehicleWheel3D"和"视觉去穿透"，都不划算、
    已回滚 —— 那次结论就是"要越野得自己写轮胎模型"，这次做了。）
  - **怎么算**（三层，`_apply_wheel()`）：
    1. **悬挂**：从"硬点在轮心上方 (rest − sag) 处"沿底盘**下方**打一条射线（长度 = rest + 半径）。够得着地面就按 `压缩量 = rest + 半径 − d` 算，轮心 = 硬点 + 下 × (rest − 压缩量) ——
    **轮胎网格挂在轮心节点上，所以视觉上跟着物理悬挂上下走**；静止时压缩量 = **负载 ÷ 刚度**
      （= 行程 / 触底倍率），轮胎底面**贴地不入地**。支撑力 = k × 压缩量 + c × 压缩速度，作用在接触点上
      （带力矩 → 压弯悬挂时车身会侧倾）。
    2. **整圈 16 射线**：从当前轮心朝轮平面里的圆周打 16 条等距射线（每 22.5°、长度 = 半径 + 0.04），
       **跟"下"夹角小于 60° 的那一片跳过**（那一片归悬挂管，不然平地上十几条射线并联，力翻十几倍、
       车会被弹飞 —— 第一版就是这么飞起来的）。剩下的方向负责探台阶/路缘/坡脚：按"压缩量 = 半径 −
       距离"收集接触深度，与主射线合并，选最深接触沿真实表面法线施力，每轮只计算一次。
       ⚠️ **判据的符号踩过坑**（2026-10-12 修）：跳过必须用 `dir · down`（下），当时写成了
       `dir · (-down)` = `dir · up`，于是跳掉的是**朝上**那一扇区、正下方那 5 条全留在场上 ——
       平地上每个轮子都多出 2~3 个接触点（正下方那条 + 压缩大了以后的 ±22.5°），支撑刚度 / 阻尼 /
       抓地随压缩量**跳变**（等于悬挂比调的硬一倍），用户那边的原话是"怎么调都飘 / 不稳 / 打方向
       一路叠加"。现在有测试上锁：`test_ring_rays_skip_the_suspension_sector_under_the_wheel`。
       **把 `wheel_rays` 写 0 = 纯单射线模式**（整圈全关，只剩悬挂那条），方便 A/B 底盘本身。
    3. **摩擦**：横向（沿轮轴）抵侧滑、纵向（轮子前进方向）给油门/刹车，都按 `mu × 法向力` 截断；
       横向滑得越快、可用**横向**摩擦越小（`wheel_slip_falloff`）—— 真轮胎过了峰值就滑，硬拐先推头，
       而不是把全部横向力灌进车身。⚠️ **衰减只作用在横向**：老版本把"前进滚动速度"也算进滑移，
       于是车一超过 `slip_ref`（12 格/秒）抓地就掉一半 —— 直线也滑、刹车也滑，手感"像在冰面上
       开车"（2026-10-12 修）。现在直线/刹车用满 mu，只有真横向搓地才衰减。
    4. **侧倾稳定器（防翻，`ANTI_ROLL`）**：有轮子着地时，绕车身前后轴给一个"回正弹簧 + 阻尼"，
       劲度 = 车重 × 重心高度 ÷ 允许侧倾角（默认 8°），阻尼 = 0.55 倍临界阻尼（转动惯量读
       `RigidBody3D.inertia.x`）。真车靠低重心 + 防倾杆，这台机器人零件权重一样、重心天然偏高，
       不给这一层 85 格/秒打方向就翻车（实测倾角 141°）。腾空时不生效。
  - **参数从哪来**：**全部**在轮轴自己的 `.part.txt` 里（`_add_wheel()` 建节点时读一次，
    每帧只查抄好的数值）。半径 = 轮胎盒子。
    **悬挂只调两项**：`wheel_suspension_travel`（最大避震行程，格，默认 1.2）和
    `wheel_support_multiple`（所有车轮触底弹簧力之和 / 初始整车重量，默认 8）。
    进场时保存初始质量 `M`、初始轮数 `N`、重力 `g`，每轮 `m = M/N`；
    `k = 倍率 × m × g / 行程`，`c = 2√(km)`（临界阻尼），自由长度等于最大行程。
    静态压缩量为 `行程 / 倍率`，硬点按这个量补偿以保留建造时的轮心高度。
    上述平衡量不含 `data/handling.txt` 的额外下压力；当前 `downforce = 0.5` 时，
    平地总静压约为 `1.5 × 行程 / 倍率`，这不会改变进场时计算的刚度和阻尼。
    多射线只探测接触；每轮合并为一次弹簧、阻尼和轮胎力，离地清空接触载荷。
    弹簧与阻尼合力限制在 `[0, 单轮触底弹簧力]`；倍率定义仅指触底时的弹簧弹力。
    毁伤更新刚体质量、重心并移除坏轮，**不会重算幸存轮的刚度、阻尼、行程和限力**。
    重新进场才生成新的快照；玩家与靶子共用初始化流程。
    旧 `wheel_stiffness`、`wheel_damper_*`、`wheel_rest_length`、`wheel_ride_sag`、
    `wheel_damper_ratio`、`wheel_suspension_max_force`、`wheel_peak_force_car_weights`
    只给出弃用提示，不再参与悬挂计算。不同轮轴使用不同倍率时，总倍率为这些倍率的平均值。
    测试见 `tests/test_suspension.gd`、`tools/test_suspension_physics.gd`。
    `scripts/test_field.gd` 顶上的 `WHEEL_*` / `ANTI_ROLL_*` 常量现在只是**默认值**
    （部件文件没写那一行时才用）。
  - **抓地力（mu）和 `wheel_friction` 的关系**（用户问过"调 5000 为什么还在滑"）：
    mu 是**直接**写在部件文件里的 `wheel_mu`（1.0 = 横向 1 g），写了就优先用它；
    只有 `wheel_mu = 0` 时才退回 `wheel_friction × wheel_mu_per_friction`（上限 `wheel_mu_max`）。
    旧版本是 `mu = clamp(friction × 0.06, 0.2, 1.2)` —— 5000 × 0.06 = 300 被夹成 1.2，
    所以 `wheel_friction` 调到 20 以上**一点效果都没有**，看起来像"这个选项没接上"。
    断言：`test_wheel_grip_is_tunable_past_the_old_cap`。
  - ⚠️ **左右镜像挂载要把滚动方向统一到车头**：`axle × sus` 只保证垂直，镜像的车轮会指向车尾，
    那样一半轮子往后推、整车原地不动（原生那套踩过同一个坑）。
  - **实测**（custom_1，平地）：静止时 8 个着地轮**轮胎底面与地面的间隙 = 0.000 格**（不再入地），
    残速 0.02；行驶中同样贴地（间隙约 0.01 格）。
  - **转向 / 防翻**（调 mu 与侧倾稳定器前后对比，同一个动作）：
    | 动作 | 之前（mu 2.0、无稳定器） | 现在（mu 1.2 + 稳定器） |
    | --- | --- | --- |
    | 高速（85 格/秒）打方向 | 倾角 141° → **翻车** | 倾角 31° → 稳 |
    | 全油门满舵连转 4 秒 | 翻车 | 最大 36° → 稳 |
  - 0.6 格高的台坎（= 轮半径的 60%）**要有一段助跑**才过得去（陡坎慢慢蹭会滑回来 —— 这一档
    本来就不是慢速能上的高度）。
  - 手感旋钮（都在 `data/parts/toywheel2x2/toy_wheel_2x2.part.txt`，调参顺序建议照这个来）：
    `wheel_mu`（抓地力，**最要紧的一个**，1.8 左右开始明显"粘地"）→
    `wheel_suspension_travel`（行程）/ `wheel_support_multiple`（触底倍率，默认 8；阻尼自动计算）→
    `wheel_anti_roll_tilt`（防翻力度，★**单位是度**，写 0 = 关掉防翻）/ `wheel_anti_roll_damping` →

    `wheel_grip_gain` / `wheel_brake_gain` / `wheel_roll_gain`（力的增益）、
    `wheel_rays`（**0 = 纯单射线模式**）/ `wheel_ray_slack` / `wheel_sus_sector`（整圈射线的形状；
    `wheel_sus_sector` 别调到 0 以下，那会让正下方的射线也参与、跟悬挂并联）。
    `wheel_ray_offset`（判定射线的**侧向偏移**，格，沿轮胎轴向、正 = 车外：0 = 轮胎中缝，
    写"轮胎半宽"（2x2 是 0.4）就把整套判定挪到**轮胎外侧面** —— 贴路缘时咬合的位置跟着变;
    挪的是射线，轮胎网格/轮心/悬挂高度都不动。左右两侧的挂载是镜像的，符号由

    实测 8 个轮子全部朝外挪 0.40 格（离车心 3.41 → 3.81）。断言：
    `test_ray_offset_goes_outboard_on_both_sides`）。
    防翻是整车效应：**取第一个轮轴**的 `wheel_anti_roll_*` 那一对值。

* **全轮转向**：`VehicleDef.wheel_specs()` 按**重心**给每个轮子一个 `steer_sign`
  （轮胎中心 x > 重心 x → +1，否则 -1），`use_as_steering = true` 全开。所以打方向时
  **重心前的轮子正转、重心后的轮子反转**——一侧轮子被打掉后，剩下的轮子照样能把车拧过来。
  断言：`test_wheel_specs`（含"重心被压到车头一侧"的极端情形）。
* **转向行程按轮轴位置分配**（`VehicleDef.steer_travel_factor()`，2026-10-18 用户要求）：
  只有**最前 / 最后**的轮轴拿满行程，偏中间的轮子按"离前后中点有多远"线性缩小
  （正中间 = 0，不转向）。以前中间轮也全额转向，多轮车转弯像在横着搓。
  实现在 `wheel_specs()` 里给每个轮轴加 `steer_factor`，`TestField` 算目标转角时乘上去：
  `target = steer_sign × steer × steer_max × steer_factor`。断言：
  `test_steer_travel_factor`（1 / 0.5 / 0 / 无跨度不缩放）+ `test_real_vehicle_wheels_have_steer_factor`。
  **转角不是瞬移**：每帧用 `move_toward` 朝目标角靠拢，角速度上限 = 部件文件里的
  `wheel_steer_speed`（度/秒，默认 90，被夹到 ≥1）。松方向键时目标回 0，同样按这个速度
  往回走 —— 打方向有"缓启动"，不会一帧打满、一帧回正。实测（120Hz）：90°/s 时每帧
  0.75°，按 A 后 3 帧只有 2.3°（满角 15°）。`test_drive.gd` 第 ④ 段会打逐帧转角。
  每个轮轴各读自己那一份，所以不同轮轴可以有不同的转向速度。
* **限速靠余弦衰减，不是硬截断**：`推力 = wheel_engine_force × 油门 × cos(π/2 × |v| / wheel_max_speed)`
  —— 0 速度时给满推力，越接近 `wheel_max_speed` 推力越小，正好到限速时降到 0。
  只在"油门方向和车速同向"时衰减（反打方向该给满推力）；所以实际极速会**略低于**
  `wheel_max_speed`（渐近逼近，不再顶着限速一顿一顿）。实测：限速 100 时车到 29.3 速度，
  每轮推力已经从 1000 衰减到 898（cos(26.4°)≈0.895）。
  `test_drive.gd` 第 ② 段会把"当前每轮推力 / 满推力"一起打出来。
* **反方向键 = 自动刹车**：`throttle` 和"前进速度"反号且速度还超过 `REVERSE_BRAKE_SPEED`
  （0.6 m/s）时，只踩刹车不给油；速度掉下来才真正反向起步。
  **速度必须取地面平面上的投影**（拿底盘 up 把竖直分量减掉）：车加速翘头、悬挂起伏、
  腾空时车头方向会上仰，三维点积算出来的"前进速度"会变成负数 —— 于是踩着 W 反而被判成
  "在反方向"，一边给油一边刹车。症状是给油 2 秒只走 2 米、末速≈0（踩过）。
* **轮子的动力 / 悬挂参数写在部件文件里**（用户自己调，每个轮轴可以不一样）。
  物理引擎是 **Jolt**（`project.godot` 的 `3d/physics_engine`），`VehicleWheel3D` 在它上面
  走 Jolt 的车辆约束：

      wheel_engine_force = 300    # 每个驱动轮的推力，N
      wheel_brake        = 400    # 刹车力。实测 400 = 6 m/s 在 0.07 秒内归零（≈一步刹停，很暴力）；
                                  # 想让刹车有过程，按 6 m/s → 0 花 0.3~0.4 秒的量级往 30~60 降。
                                  # 注意：没有抓地力时（轮子离地）刹车力几乎不起作用，刹车靠轮胎。
      wheel_max_speed    = 30     # 到这个速度推力衰减到 0（余弦，不是硬截断），m/s
      wheel_steer_max    = 24     # 最大转角，度（0 = 不转向）
      wheel_steer_speed  = 90     # 转向角速度，度/秒（越大越跟手；缓启动的速率）
      wheel_radius       = 0      # 0 = 按轮胎模型自动算
      # 抓地力（★）：wheel_mu 直接给库仑摩擦系数；写 0 才用 wheel_friction × 换算比例
      wheel_mu / wheel_mu_per_friction / wheel_mu_max / wheel_friction
      # 滑移衰减 / 力的增益 / 整圈射线 / 悬挂 / 防翻
      wheel_slip_falloff / wheel_slip_ref / wheel_grip_gain / wheel_brake_gain / wheel_roll_gain
      wheel_rays / wheel_ray_slack / wheel_sus_sector
      # 悬挂：进场时按初始车重和轮数求出刚度、临界阻尼，毁伤不重算
      wheel_suspension_travel = 1.2   # 格
      wheel_support_multiple = 8     # 总触底弹簧力 / 初始车重
      wheel_anti_roll_tilt / wheel_anti_roll_damping      # 整车共用：取第一个轮轴（tilt 单位 = 度）

  `_add_wheel()` 建节点时读一次（每帧只抄下来的数值，不查表）；解析失败保留默认值并告警，
  不会出现"参数写歪 → 车不动"。断言：`test_wheel_parameters_live_in_the_part_file` /
  `test_wheel_tuning_keys_are_parsed_and_guarded`。**实际能调的键名以
  `toy_wheel_2x2.part.txt` 里带注释的那一份为准**（那份是给用户看的清单）。
* **动力 vs 翘头（调参时看这条）**：车会不会一给油就抬头，只看两个数 ——
  可用加速度 `驱动轮数 × wheel_engine_force / 整车质量`，和翘头门槛
  `g × (重心到后轴的水平距离) / 重心离地高度`。可用的比门槛大就抬前轮（数据层没有防翘头，
  这是物理该有的结果）。实测：3 格车（轴距 2 格、重心离地 1.47）门槛 6.4 m/s²，
  4 轮 × 300 N / 91 kg = 13.2 m/s² → 一给油就翘头立起来（最大倾角 91°）；
  6 格车（轴距 5 格）门槛 15.5 > 12.8 → 正常跑。用户的 `custom_1`（51 件、136 kg、
  重心离地 1.58、门槛 19.2）远在门槛以内。
* **轮胎的视觉转动是我们自己驱动的**，不跟 `VehicleWheel3D.get_rpm()`：滑行时它恒为 0
  （实测 10 m/s 滑行、4 轮着地读数 0.0，按车速算应该是 93 rpm），给油时又乱跳 ——
  表现就是"轮子随机乱转"。`TestField._spin_tire()` 的做法：
  1. 物理上正确的滚动角速度 `ω = up × v / 半径`（无滑移滚动的定义：接地点相对地面静止）；
  2. 轮胎自己的转轴在世界里的方向 = `(轮子节点世界朝向 × child_basis) × (1,0,0)`；
  3. 把 ω 投影到这根轴上积分成角度，作为**零件本地 x** 的旋转贴到网格上；
  4. 绕**轮胎中心**转（零件本地的 `local_centre` = 轮胎自己坐标系里的 y=16、z=16）：
     平移量必须跟着旋转一起算 `-(child × R × centre)`；写成固定的 `-(child × centre)`
     就等于绕**零件原点**转 —— 原点到轮胎中心差 0.5 格，轮子会一边转一边画圈；
  5. 正在输出（`engine_force ≠ 0`）时按"虚拟速度"多给 `TIRE_SPIN_INDICATE`（0.6 圈/秒），
     所以**静止踩油门也看得出轮子朝哪转**；刹车时不叠加（刹车 = 没有输出，轮胎照旧往前滚），
     整体再被 `TIRE_SPIN_MAX`（2.5 圈/秒）夹住，不会快得看不清。

  **两个坑（都是实测出来的）**：
  - `VehicleWheel3D` 把自己的节点朝向设成**镜像**的（实测 `det(零件→世界) = -1`，本地 +y 朝下）。
    镜像帧里"绕本地 x 转 +θ"在世界里是绕 -x 转 θ —— 不乘 `det` 四个轮子会整齐地**倒着滚**
    （实测同向度 -1.00 ×4）；
  - 转轴和转速**全程用世界量**算，不要用"节点本地 -z 是不是车头"来判断朝向：左右两侧的轮轴是
    镜像挂载的，那个约定会把一半轮子算反（实测同向度两两不一致：-0.35 / -0.73）。
  验证见下一条的 ⑤ 段。
* **武器 = 转塔（轻机枪，`scripts/turret.gd`）**：一个部件里放**三个子模型** ——

* **相机 = 鼠标自由环视**（不自动回正，瞄准要靠它），视线被墙挡住自动贴墙；
  **不做位置平滑**（相机硬贴在环视位置，转视角没有拖影）。

  相机朝向会瞬间失效 → **画面闪一下别的视角再回来**（2026-10-18 用户报的 bug）；

  ③ 反向键先刹车（打印每 0.067 秒的速度轨迹）④ 全轮转向（各轮实际转角 + 车头转了多少度）
  ⑤ 轮胎视觉转动：世界转动方向必须和 `up × v` 同向、轮胎中心在自身节点坐标里的偏移必须 ≈ 0。

  | 车 | ② 给油 1.5s | ③ 反向键 | ④ W+A 1s |

  | 3 格（轴距 2） | 位移 2.0 m、最大倾角 91° → 翘头翻车 | 5.8 → 0.4 → 倒车 | 翻着，无意义 |
  | 6 格（轴距 5） | 位移 11.7 m、末速 15.8 m/s、最大倾角 3° | 6.0 →（0.07s 内）0 → 倒车 19.8 | 车头 -29°（A = 左）、各轮 -24°/-24°/+24°/+24° |

  ⑤ 两台车都是 `+1.00 ×4`、中心跑偏 `0.000 格`（转过之后如果要改 `_spin_tire()`，
  先跑这一条：方向反了或中心取错，看数字最快）。
  改了轮子/底盘代码后跑一遍 —— 轮子好不好使看代码看不出来。
* **卡顿**：`project.godot` 开了 `physics/common/physics_interpolation=true`。
  物理按 60Hz 跑、渲染按屏幕刷新率补间，不开的话开动起来的载具会"一格一格跳"，
  看着就是卡（静态的建造界面看不出来）。手动摆的相机（建造模式 / 测试场）要设
  `physics_interpolation_mode = OFF`，否则会被拉回旧的物理位置。
  ⚠️ **`project.godot` 里别写中文 / 带引号 / 带等号的注释**：Godot 保存项目设置时会把这种
  注释和**下一行**粘成一个假键（`"注释文字…真正的键名"=值`），于是真正的设置**静默失效**。
  这个坑真的踩过：`common/physics_interpolation` 被粘进了假键里 → 插值一直是关的，
  修法是把注释全改成纯 ASCII（`project.godot` 里现在就是这么写的）。
* **世界的标定：1 cube = 0.5 米**（2026-10-14 从 0.2 米改过来 —— 用户判断"手感问题很大
  程度上是比例尺问题"：车还是 25 格长，但 30 m/s 从 150 格/秒 变成 60 格/秒，相对车身慢下来、
  稳下来）。引擎本身只认"格"，所以标定靠两个数落实，**必须一起改**，否则世界自相矛盾：

  | 位置 | 值 | 换算 |
  | --- | --- | --- |
  | `PartDef.CUBE_METERS` | **0.5** | 1 格 = 0.5 米（唯一来源） |
  | `project.godot` → `physics/3d/default_gravity` | **19.6** | 真实 9.8 m/s² ÷ 0.5 米/格 |
  | `TestField.ARENA_SCALE`（城镇模型倍数） | **5** | 模型单位≈米 ⇒ 5 个模型单位 = 1 格 |
  | 部件文件里的**力/弹簧/阻尼** | **不动** | 它们是"格世界"里的数，决定 `a/g`（手感） |

  常量 `PartDef.GRAVITY_CUBES := EARTH_GRAVITY / CUBE_METERS` 把"重力"这件事收成一处；
  `TestField._world_gravity()` / `Projectiles.gravity` 都引它。断言（三者一致性哨兵）：
  `test_world_calibration_is_consistent` —— 它会抓"改了 CUBE_METERS 忘了改 project.godot"。

  ⚠️ **部件文件里的"速度"一律写真实 m/s**（2026-10-12 统一）：换算只做一次，
  常量是 `PartDef.CUBE_METERS`（测试场那个 `CUBE_METERS` 直接引它）。
  现在 `wheel_max_speed = 30`（m/s = **60 格/秒**）、`weapon_muzzle_speed = 500`
  （m/s = **1000 格/秒**）。断言：`test_wheel_max_speed_is_in_real_meters_per_second`。

  **力和弹簧为什么不跟着动**：标定只决定"一格有多大"，而手感来自 `a/g`（动力/重力比）与
  几何比例。重力跟着标定走（19.6 = 9.8÷0.5）之后，**重力相对几何变弱 2.5 倍** —— 跳跃更远、
  过弯半径相对车身更小、同样的力显得更冲。这就是这次改标定想要的"手感变化"本身：
  以前 0.2 米/格的那套是"重力相对几何大 5 倍 = 世界很小 = 像卡丁车"。
  想把 `a/g` 拉回旧值：把轮子文件里的力 ÷ 2.5（旧值 ×5 的那批现在 ×2 即可）。
  运行时也能改重力：`ProjectSettings.set_setting(...)` 或
  `PhysicsServer3D.area_set_param(space, AREA_PARAM_GRAVITY, v)`，按车单独改用
  `RigidBody3D.gravity_scale`。
  测试场 HUD 常驻显示 FPS 和物理耗时，方便区分"渲染帧率低"还是"物理步进抖动"：
  物理实测 0.4 ms、整机一千多个三角形 —— 这个规模的问题基本都在步进上，不在渲染量上。
  **踩过的坑（务必保留哨兵）**：曾经把整段 `_build_arena()`（环境光 + 方向光 + 地板）
  误贴进 `_unhandled_input()` 末尾 —— 于是**每一个鼠标/键盘事件都再建一套光照和地板**，
  鼠标一动就是几十套/秒。症状：静止 2~3 FPS、开起来更低、draw/图元成倍上涨。
  现在的防线：
  1. `TestField._ready()` 有 `_built` 幂等闸（和主界面一样），脚本重复 ready 也不会重建；
  2. `enter_vehicle()` 换车前先 `queue_free()` 掉旧底盘，换车是"替换"不是"叠加"；
  3. HUD 常驻显示 `网格 / 场地 / 载具` 三个计数 —— 正常是一只手的数，几百就是被重复建了；
  4. `godot --path <项目目录> --script res://tools/inspect_field.gd [车辆id]`（要窗口）
     会点清节点、读 draw/图元、**再灌 400 个输入事件复核节点数不变**，最后等静置 3 秒
     报稳态物理耗时；开头还会打**质量 / 重心 / 每个轮子的转向符号**（全轮转向的前后分界
     有没有分错，看这几行）。基准：`custom_1`（51 件）→ 网格 9 / WorldEnvironment 1 /
     draw 56 / 图元 5130 / 物理 0.5 ms / FPS 三位数。

零件的网格是绕**格子角点**旋转的，所以侧面建造时直接写 `Transform3D(basis, 格子角点)`
会让旋转后的几何体甩到隔壁格：**记账说在 A 格、画面里却在 B 格**。
正确做法是让「新零件默认连接点 = 目标面面心」求出平移量（`placement_transform`），
它与「旋转后 AABB 最小角对齐格子角点」（`cell_transform`）必须等价。
`test_placement_lands_in_the_adjacent_cell` 对 2 种零件 × 6 个命中面 × 4 个滚转档
逐一验证这条（96 条断言）。

### 全局手感辅助（下压力 + 自动回正，参数在 `data/handling.txt`）

轮胎手感调不出"丝滑"时，不想再逐车轮去抠 `wheel_*`，就加了一层**整车级**的辅助：
两条都在 `TestField._apply_handling_aids()`（每帧 `_drive_vehicle()` 末尾，紧跟防倾杆之后），
参数全在 `data/handling.txt`（和 `data/audio.txt` 同一套"`键 = 数值` + `#` 注释"解析，
按文件修改时间缓存，**改完进一次新场景就生效**）。

* **① 下压力**（模拟气动力）：`downforce` × **当前车重**（N），方向**世界下方**，作用在质心。
  系数就是"**多少倍车重**"（无量纲）：0.5 = 一直额外压上半个车身重量。压车身 → 悬挂压紧 →
  轮胎法向力大 → 抓地大。**不随速度变**（2026-10-13 从"×速度²"改过来 —— 用户要的是
  "一直更贴地"，不是"越快越贴"）。车重取**当前**值：`VehicleRig.sync_body()` 在零件被打掉后
  会把剩下的重量写给 `chassis.mass`，所以车变轻、下压力跟着变小。
* **② 自动回正力矩**：把车身 up 往世界竖直拧（滚转 + 俯仰都管）。`upright_torque` 是
  **"倾到 90° 时"** 的力矩（N·m），实际按 `sin(倾角)` 缩放 → 越歪越拉、正了就松手
  （`up == 世界up` 时返回 0，平地不会自激发抖）。`upright_damping` 是相对**临界阻尼**
  的系数（1.0 = 刚好不回摆），只吃**倾斜速率**、不碰绕车身 up 的自转。
  ⚠️ 轮子文件里的 `wheel_anti_roll_*`（只防滚转）和它是**叠加**的 —— 两个一起开会很硬，
  建议只留一个（想要这套就先把 `wheel_anti_roll_tilt` 写 0）。
* **只在地面上时生效**：**有轮着地 = 满效果，一个都没着地 = 完全不生效**（不按着地轮数
  比例缩放 —— 压着两个轮子也算满，2026-10-13 改）。中间用 `ground_blend_seconds`
  （秒）线性过渡，所以落地是平滑恢复、不会"啪"地跳一下；写 0 = 立刻切换。
  实现：每台车自己的 `handling_blend` 状态 + `TestField.handling_blend()`。
* **③ 松手回正（偏航）**：`yaw_center_seconds` = **时间常数（秒）**。高速打方向再松手，
  车身还会"自己转一会儿"才直 —— 这一条治它：**只在没给转向输入时**把绕车身 up 的
  角速度按这个时间常数衰减（τ = −I·ω / 秒）。0.35 = 0.35 秒掉到 37%、1 秒基本不转；
  0.20 更利落、0.80 更溜；0 = 关掉。因为只在"松手"时生效，**打方向那段的转向手感一点不变**。
  ⚠️ 它不管滚转 / 俯仰（那是 ② 的活），也不管转弯半径 —— 它只是把"松手后车还在自转"这件事按时间掐掉。

数学细节（都写成静态函数，测试能不启物理直接验）：
`TestField.upright_torque(up, angular_velocity, max_torque, inertia, damping)` ——
方向 = `up × 世界up`（绕它正转是"最短路径"把 up 转到竖直），大小 = `max_torque × sin(倾角)`，
再减一份 `tilt_rate × 2√(max_torque × inertia) × damping`。
`TestField.yaw_center_torque(up, angular_velocity, seconds, inertia_up)` ——
只取绕 `up` 的那一份角速度，出力矩 `−I·ω / seconds`（时间常数衰减）；
`TestField.inertia_about(轴, 车身basis, RigidBody3D.inertia)` 把**本地**对角惯性投到世界轴上
（Godot 的 `inertia` 是车身本地 x/y/z 的分量，不是世界坐标的）。
⚠️ Godot 的 `RigidBody3D.inertia` **有时读出来是全 0**（形状还没同步给刚体），而 ②③ 的阻尼项
都乘着它 —— 那样会静默变成"没效果"。所以 `_inertia_of()` 做一次合理性检查：张量总和连
`box_inertia_guess()`（实心长方体 `m(a²+b²)/12`，用整车包围盒）的 3% 都不到就换成粗估值。
断言：`test_upright_torque_twists_up_toward_vertical`（判据 `(τ × up) · 世界up > 0`）、
`test_upright_damping_only_brakes_tilt_rate`、`test_yaw_center_torque_brakes_only_yaw`、
`test_inertia_about_world_axis`、`test_steer_return_speed_falls_back_to_steer_speed`、
`test_handling_blend_switches_on_any_contact`、`test_handling_table`。

**转向角"回中"速度**（在轮轴部件文件里，不在 handling.txt）：`wheel_steer_return_speed`
（度/秒）= 松开方向键后转角回 0° 的速度，**和打方向的 `wheel_steer_speed` 分开**。
不写 = 跟 `wheel_steer_speed` 同速（老行为）；`toy_wheel_2x2.part.txt` 现在写 240
（打方向仍是 60，所以"缓启动 + 撒手就正"两者兼得）。

### 调试提示：改了脚本要重启，别被旧进程骗

Godot 的游戏进程**不会热重载脚本**：改了 `.gd` 之后，正在跑的那一局会一直用旧代码，
表现成“我明明改了却没生效”。编辑器侧同理（改完要让编辑器重扫一次）。
本轮就踩过一次：症状是“斜坡建不了也删不掉”，实测是运行中的 `BuildGrid` 还是旧的
（体素步进用射线原点算起点那版），而磁盘上的代码已经是修好的版本。

判断办法：在游戏里直接读运行中脚本的源码比对，例如
`grid.get_script().source_code.find("entry_t")` —— 找不到就是旧版。

测试怎么跑：编辑器里 MCP 的 `test_run`（`tests/test_*.gd`，`extends McpTestSuite`），
或者命令行 `godot --headless --path <项目目录> --script res://tools/run_tests.gd`。
**⚠️ 测试用的临时文件绝对不要放在 `user://` 下并叫 `test_*`**：这套发现机制把
`user://test_*.txt` 也当成脚本去加载，于是"上一次跑挂留下的残留文件"会把整套测试
带崩（症状是 `Parse Error: Unexpected "Identifier" in class body`，指向那个 txt）。
统一用 `user://tmp_*`。断言失败时函数**不会中断**，所以清理语句通常仍会执行 ——
但别指望它。


### 性能：建造模式的每帧路径上不许重建体素

建造模式每帧都要跑 `plan() → can_place() → mesh_clash() / face_coverage()`，
而 `world_bounds()` 在这条路上会被问几百次。踩过的坑：`PartDef.mesh_bounds()` 曾经写成
“先 `build_volume()` 再看缓存”，可解析形状零件（`cube_full` / `half_cube`）的
`build_volume()` **每次都会重建 4096 体素** —— 结果就是“一拿建造枪瞄准就卡死”。

现在的做法：

* `mesh_bounds()` 只算一次并缓存；模型文件换了的失效交给 `model_volume()` 标脏
  （render / build 那条路会走到它）。
* 零件的世界包围盒在**落子时**算好存进 entry 的 `bounds`，`mesh_clash()` 直接拿来比，
  整体平移时跟着搬。
* `face_coverage()` 直接扫体积的扁平数组（`volume.data` + 自己算 stride），不走 `is_solid()`。
* 建造模式里“瞄准输入没变”（同一个格子 / 朝向 / 零件，没滚转，场地没改动）就整帧跳过
  `plan()`；HUD 文字没变也不重排（`_aim_key` / `_grid_epoch` / `_hud_text`）。
  镜像开关和对称面位置也在 `_aim_key` 里，所以按 `M` / `【` `】` 会立刻重算。

实测（216 个方块的场地，单次 `plan()`）：卡到跑不完 → 3.06 ms → **0.39 ms**。

  5000 个三角形，一个 trimesh 碰撞体）。2026-10-18 用户要求从 1 公里缩到一半。
* 起伏 = 四层正弦叠加：实测落差 **18.5 米、最陡 6.6°**；生成后还有一道
  `_clamp_pair()` 把相邻格高差夹到 `tan(20°) × 格距` 以内 —— **20° 是硬上限**（用户要求）。
* 地面颜色按高度 / 坡度 / 三档色斑刷顶点色，一个 draw call；没有贴图素材。

  每堆 55 米半径 —— 地图上有几处像样的交火点，而不是把石头均匀撒满 1 平方公里。
  每个掩体一个 `StaticBody3D` + BoxShape（按包围盒 88%），和地面同在第 1 层。
* 装饰：树 130 / 灌木 170，MultiMesh 一批画完，**不参与碰撞**（省物理，也不会让人机撞树）。

### 队伍 / 友军伤害

碰撞层：1 = 地形，2 = 我方车体，3 = 敌方车体（`AIM_LAYERS` 三层都包含）。
敌我判定不看层，看 `VehicleRig.team`：`_on_projectile_hit()` 里
`_team_of_key[owner_key] == rig.team` 就直接返回 —— **队友打队友不掉血**（火花照放）。
关闭友军伤害的原因：10 台车挤在一起，误伤会让"谁在打谁"完全看不懂；
人机的瞄准也会被队友挡枪（见下）。

### 人机（`BattleMode._ai_*`）

每物理帧一次，没有寻路（开阔缓坡 + 前方射线 + 卡住倒车就够了）：

1. `_ai_target()`：最近的、还活着的敌人，每 `bot_retarget_seconds` 秒或目标死了才换；
2. `_ai_aim_point()`：目标重心 + **提前量**（`lead_point()`：速度 × 距离 / 初速）；
3. `_ai_sees()`：从车顶到目标重心打一条射线（地形/掩体/别的车挡住 = 没看到）；
4. **反应时间**：看到敌人（视线通）后要等 `bot_reaction_seconds`（默认 **0.3 秒**）才允许开火；
5. **瞄点随机偏差**：刚看到时瞄点相对核心随机偏最多 `bot_aim_spread_deg`（默认 **2°**），
   偏移量 = `tan(角度) × 距离 × decay`；连续开火 `bot_aim_settle_seconds`（默认 **2 秒**）内
   decay 从 1 线性降到 0（越打越准）；**换目标 / 视线断了重新发现 → 偏差和反应计时重置**；
6. `_ai_can_fire()`：距离 ≤ `bot_fire_range`、某台转塔的枪口与瞄准方向夹角 ≤
   `bot_aim_tolerance`、从枪口到瞄点的射线**先打到的不是地形、也不是队友**；
7. 行驶：远了冲（油门 1）、近了倒（油门 -1）、中距离绕圈（`bot_standoff`），
   转向 `steer_towards()`（+1 = 左，和玩家按 A 一致）；
8. `_ai_avoid()`：前方 `bot_probe` 格打一条射线，撞到就往空的一侧偏 `bot_avoid_angle`；
9. 卡住检测：给油但速度 < `bot_stuck_speed` 超过 `bot_stuck_seconds` → 倒车 `bot_reverse_seconds`。

**所有参数都在 `data/battle_ai.txt`**（`键 = 数值`，`#` 注释；改完重新进一次战局就生效）：
`bot_standoff`（绕圈距离）、`bot_too_close`（倒车距离）、`bot_fire_range`、`bot_aim_tolerance`、
`bot_retarget_seconds`、`bot_stuck_speed`、`bot_stuck_seconds`、`bot_reverse_seconds`、
`bot_probe`、`bot_avoid_angle`、`bot_reaction_seconds`、`bot_aim_spread_deg`、
`bot_aim_settle_seconds`。

人机的车 = `data/vehicles/bot_light.vehicle.txt`（16 件 / 4 轮 / 1 枪）和
`bot_gunner.vehicle.txt`（17 件 / 2 枪），都是能正常开、有核心的合法整机（由建造网格生成，
`robot_status()` 通过）。**要调人机强度就改这两个文件**（多装一把枪立刻变强）。

### 性能优化（2026-10-19：10 台 293 零件的 "111" 一起跑）

症状：双方 10 台都是 `custom_1`（293 零件 / 10 根轴 / 6 转塔）时，release 也常掉到 30 以下。

**根因是"每个零件一个碰撞盒挂在刚体上"**：10 × 293 = 2930 个盒子和地形 trimesh 做接触查询
（实测物理 **21 ms/步**、9 FPS；同样 10 台 16 零件的轻车只要 10.8 ms）。逐项改：

1. **车体地形碰撞 = 全部方块贪心合并**（`VehicleRig._add_chassis_hull()`）：
   * **轮轴 / 核心 / 炮塔底座**这些不动的部件**全部**并进合并盒（用户 2026-10-19 的要求）；
   * 方块（含半砖/角块 —— **地形碰撞一律按整格算**）按整数格**贪心合并**成矩形盒子
     （`_greedy_merge()`：先沿 X 拉长、再沿 Z 铺宽、最后沿 Y 叠高），掉零件时限流 0.2 秒重建；
   * 唯一的例外：部件文件里 **`weapon_swivel_collider = true`** 的炮塔给支架一个独立碰撞盒
     （体积小的枪用 false，省一个 shape；以后做"跟着水平旋转的碰撞盒"的大炮塔再打开）。
   实测 "111"（293 零件）：**0 个独立盒 + 23 个合并盒 = 23 个 shape**（原来 293）；
   10 台车 8 秒：**FPS 74~77、物理 8.4 ms/帧**（纯一件一盒是 22~25，整车方盒是 85~99）。
   断言：`test_swivel_collider_flag`（默认并进合并盒；打开开关后炮塔单独一盒且对应零件下标）。
   备选：`_rebuild_chassis_hull()` 那个"带 `HULL_BEVEL` 裙边倒角的凸包"（单 shape）。
   原来是一个 AABB 方盒，但方盒的**平底 + 直角**上坡时会铲进地形、把车卡在坡上（用户 2026-10-19 报的）；
   改成"每个零件一个盒子"实测 10 台车 **FPS 22~25**（293 个 shape/台，不可用）；最后折中成
   **一个凸包**：外形仍是整车轮廓，但底面向内收 `HULL_BEVEL = 0.35` 格再抬高，形成裙边斜面。
   掉零件时重建（跟着残骸缩）。实测 10 台重车：**FPS 64~66、物理 10.2 ms/帧**（方盒时 85~99 / 7.8 ms）。
2. **零件级受击搬到 `hitboxes`**（静态 `StaticBody3D`，层 4 / 掩码 0，不参与物理）：
   所有零件盒 + 轮胎盒合成**一张 trimesh**（`_rebuild_hitbox_trimesh()`）。命中后靠
   **命中点落在哪个零件盒里**反查零件（`part_index_of_hit(..., point)`，命中很稀疏，O(零件数) 够用）；
   零件被打掉后**立刻重建**（换一个新的 `CollisionShape3D`，不是改 shape 资源）：
   - ⚠️ 重建**不能**被 `flush_visuals()` 里"没有脏视觉组就 return"的早退挡住（会永远不更新）；
   - ⚠️ trimesh 必须 `backface_collision = true`（六个面用的是同一套顶点顺序，有一半是背面）；
   - ⚠️ 重建出来的三角形是**当前活着的零件**：不重建的话"打剩一个核心"时子弹还打在已经不存在的
     零件上，命中点反查不到活零件 → **打中不掉血**（2026-10-19 用户报的 bug）；
   - ⚠️ **有零件掉的这一帧就立刻重建**（2026-10-19 用户要求，之前限流 0.2 秒太慢）：
     残影会让准星打在"已经不存在的零件"上、看着就是"瞄着却打不中"。
     一次重建 ~3.8 ms（303 个盒子），只有真掉零件的帧才触发，而且零件越掉越便宜；
   - ⚠️ 三角形必须**朝外绕**（每个面按外法线检查、反了就翻过来）：六个面用同一套顶点顺序时
     有一半是背面，而 `backface_collision` 在 Jolt 下靠不住 —— 从上往下打（准星瞄车顶）的射线会
     **穿过**受击盒，看着就是"瞄着车顶却打天上"（用户 2026-10-19 报的）；
   - `Projectiles.hit_filter`（测试场注入 `TestField._hit_is_real()`）仍然保留，作为**兜底**：
     万一命中点反查不到活零件（数值误差 / 重建那一帧的竞态），子弹会 `_pass_through()`
     **穿过去**继续打后面的东西，而不是被吞掉（"虚空挡伤害"）；
3. **子弹射线忽略车体**（`Projectiles.ignore_rids`），自己的判定登记**车体 + 受击盒两个 RID**
   （`hit_plan()` 支持数组）—— 否则"打自己"会算成伤害；
4. **人机/靶子的整圈射线压到 0 条**（只剩悬挂那条；玩家仍是 16 条）；
5. **人机轮胎每两个物理帧算一次**，另一帧直接沿用上一 tick 的接触力（延迟 8 ms，看不出来）；
6. 射线查询对象**复用**（以前每条射线 new 一个 `PhysicsRayQueryParameters3D` + 一个 exclude 数组）；
7. 引擎音效：调参进场缓存、超过 3D 声部最大距离直接跳过、每 2 个物理帧更新一次
   （1.53 → **0.05 ms/tick**）；轮胎自转只在 200 米内更新；
8. 掉零件后**射界按需重算**（2026-10-19 第二轮优化）：射界只取决于**枪管扇形** ——
   `Turret.may_be_affected_by(box)` 用"转点为心、枪管长度（转点→枪口）为半径 + 盒子半对角线"
   （和 `rebuild_arc()` 的预筛同一套口径，**不加 2 格余量**），再排除水平射界（`weapon_yaw_limit`）
   之外的零件；只有命中的转塔排进队列，每车每帧最多重算 1 台（一台 ~1.1 ms，6 台全算就是 6.7 ms/轮）。
   实测 8 秒实战 24~37 个零件损失 → **只重算 9~14 次**（按旧逻辑约 150~220 次）；
   `TestField._arc_rebuilds` 是累计计数器。
9. **伤害结算按帧打包**（2026-10-19，用户朋友的建议 + 查到的同类做法）：高射速机炮一秒几十上百发，
   逐发 `apply_damage()`（连通性检查 / 禁用 shape / 同步质量重心）+ 逐套毁伤善后是集中交火掉帧的主因。
   现在 `_on_projectile_hit()` 只把伤害**累加**到 `_damage_batches`（每车每零件一份），
   `_physics_process()` 末调 `_flush_damage_batches()`：**每车每零件每帧只结算一次**，
   死了的零件合并成一次 `_on_parts_destroyed()`（碎片也只爆一簇，位置取这一帧最后一次命中点）。
   同类参考：Unity 的 `RaycastCommand.ScheduleBatch`（一批射线合并成一个 job）、
   按 tick 结算伤害的服务器模型（低 tick 率会有假命中/延迟结算的取舍）。
   命中点反查零件也改成 **O(1) 格子表**（`VehicleRig._fill_cell_map()` / `_cell_part`）：
   3000 次微基准 **273 → 100 µs/次（2.7×）**；找不到时仍退回原来的线性扫兜底。
   断言：`test_part_lookup_fast_path_matches_brute_force`（快路径必须和暴力扫结果一致）；
   **开火音效也按帧合并**（`_queue_shot_sfx()` / `_flush_shot_sfx()`）：一帧最多播 `SFX_MAX_PER_FRAME = 3` 发，
   优先离镜头近的，被丢掉的按数量补音量（+6 dB 封顶）—— 60 台枪同时打时不再每发都抢一个 3D 声部。
   分段实测（10 台车混战，每 tick）：**轮子 8.7~9.4 ms**（最大头）、射界 1.5~1.7、AI 1.3~1.4、
   武器+射弹+伤害+音效合计 **0.5~1.0 ms** —— 射击链路已经不是瓶颈了。
10. 零件受击的视觉重建/射界/trimesh 全部**每物理帧合并一次**（见 `flush_visuals()`）；
   受击盒 trimesh **有零件掉的这一帧就重建**（3.8 ms / 1 万多个三角形，只在该帧付一次）。

2026-10-19 再降一档（用户要求"轮子射线 16→8、物理频率减半"）：
`WHEEL_RAYS = 8`、`physics_ticks_per_second = 60`。10 台重车实测 **FPS 143~144、物理 8.4 ms/帧**
（之前 120 Hz + 16 射线：32~36 FPS / 11~12 ms）。轮子数学占主线程时间减半，是这次收益的来源；
代价是悬挂/轮胎响应频率从 120 变成 60 Hz（物理插值仍开着，画面不受影响），手感要用户实测确认。
⚠️ 60 Hz 下**不能**再把 AI 轮子降到 20 Hz（`BOT_WHEEL_INTERVAL = 3` 试过）：悬挂力过期 50 ms，
车离地了力还在往上顶 —— AI 车会**不停弹跳**（竖直速度 6 秒翻转 13~20 次、峰值 8~12 格/秒，用户 2026-10-19 报的）。
现在 `BOT_WHEEL_INTERVAL = 1`（每帧算，60 次/秒，和"以前 120 Hz × 隔帧"总量一样）：翻转降到 1~3 次，
10 台车混战 **FPS 126~127、物理 11~13 ms/帧**。

结果（同一台机器、debug 版、8~15 秒实战）：物理 **21 → 8 ms/步**，物理 tick 稳定 120/s，
重车场景 FPS **9 → 31~53**（受机器负载影响）；轻车场景 5.1 ms/步、144 FPS。

⚠️ **改这些地方时注意**：射界判定（`Turret.rebuild_arc()`）读的是 `VehicleRig.part_boxes()`
（每零件本体盒），**不是**车体的 shape（车体现在只有一个整车盒，拿它会把射界全堵死）。

### 建造模式的"零件多了就卡"（2026-10-19 追加）

建造时每放一块零件都会走 `BuildMode._rebuild_parts()`：整张 `PlacedParts` 重建 + **连接点标记全量重扫**。
实测 400 件时一次 **52 ms（最慢 81 ms）** —— 每放一块就卡一下，越造越卡。

改法：
* **放零件改成增量追加**（`_append_parts(from_index)`）：往已有的 MultiMesh 里追加一个实例
  （容量按 64 起步翻倍预留，只用 `visible_instance_count` 加减；扩容会清空实例数据，所以扩容后重写一遍），
  不再整表重建。实测 **0.33 ms/块**；
* **拆零件只重建"被拆到的那一组"**（`_remove_parts()` → `_rebuild_group()`，2026-10-23）：
  一开始试过"把末尾实例搬到被删位置 + `instance_count -= 1`"，结果出现**幽灵零件**
  （格子里还有、外观没了）—— 根因是 Godot 里改 `MultiMesh.instance_count` 会**清空所有实例数据**，
  swap/缩容很容易和 `entries` 错位。现在改成按组重建（O(这一组的零件数)，400 块同类 ~0.6 ms），
  视觉和格子**一定对得上**；连接点标记仍交给限流重建；
* **连接点/基准格标记限流重建**（`_markers_dirty` + `_markers_due`，最多 6 Hz）：
  放零件时只追加那一件的标记（`_append_markers()`），拆零件时才整表重扫，而且不阻塞这一帧。
  整表重建从 52 ms 降到 **0.6 ms**。

### 零件破碎碎片（2026-10-19 追加）

零件被摧毁时炸出几块**体素碎片**：纯视效 —— 没有碰撞、不参与物理、不挡子弹。

* `scripts/debris.gd`（`Debris`，`MultiMeshInstance3D`）：所有碎片装进**一个 MultiMesh**（每块一个实例 +
  顶点色），几百块也只占 1 个 draw call；`burst()` 在零件位置炸出 `CHUNKS_PER_PART = 5` 块；
* 运动：初速（随机方向 + 向上）继承车体速度的一部分 → 重力 → 空气阻尼 → 自转，
  寿命 `CHUNK_LIFE = 1.15` 秒，最后 0.3 秒缩小消失（不玩透明度，省一份透明材质）；
* **颜色直接来自零件本身**：`PartDef.debris_palette()` = 这个零件用到的**所有体素颜色**
  （去重、最多 12 种，第一次算完缓存）；每块碎片随机挑一个，再乘 0.85~1.15 的亮度抖动 ——
  所以多色零件（机枪：黑管 + 军绿 + 黄）炸出来是混色的，单色零件就是它自己的颜色；
* 触发点：`TestField._on_parts_destroyed()` → `_spawn_debris(veh, rig, dead, hit_point)`：
  **碎片爆在子弹的命中点**（`DEBRIS_HIT_RADIUS = 2.5` 格内的死零件都算这一处）；
  以前按"每个死零件盒的中心"爆，一发穿透串起来的断连零件可能分布在全车，看着就是
  "打这里、别处虚空爆炸"（用户 2026-10-19 报的）。碎片只继承 **35%** 车速（继承太多会拖出一串"虚空"碎片）；
* 上限 `MAX_CHUNKS = 240`（满了顶掉最老的），一帧最多迭代这么多块 —— 开销可以忽略。
* 断言（`tests/test_debris.gd`）：炸出固定块数 / 会动 / 受重力 / 寿命到了清空 / 池子上限 / 颜色来自零件。

### 头顶血条 / 名字 / 小地图 / 底部状态条（2026-10-18 追加）

* **底部状态条**（`scripts/battle_combat_hud.gd`）：屏幕底部中央一条**蓝色能量条**
  （宽度 = 屏幕的 `BAR_WIDTH_RATIO = 0.5`，离底边 28 像素），左边一个**绿色血圈**
  （圆弧 = 剩余全部零件生命值 / 满血，圈里写百分比；玩家被打光时显示 `--`）。
  全部 `_draw()` 画、分辨率无关；`bar_rect()` / `health_center()` 是纯函数，
  测试 `test_combat_hud_layout` 钉住了"半屏宽 / 居中 / 血圈在左边且在屏幕内"。
* **血条 = 剩余全部零件生命值 / 满血**（`VehicleState.health_fraction()`，`hp` 数组求和），
  名字在血条上方、同色；**我方蓝 `(0.36,0.62,1.0)`、敌方红 `(1.0,0.32,0.28)`**
  （`BattleMode.FRIENDLY_COLOUR / ENEMY_COLOUR`，测试 `test_team_colours_are_blue_and_red` 守着）。
  人机没有用户名，直接用**载具名**（`bot_*.vehicle.txt` 里的 `name`，即"人机·轻型"/"人机·双枪"）。
* 画法：`scripts/vehicle_nameplates.gd` —— **屏幕空间**（`Camera3D.unproject_position`），
  按距离缩放（`SCALE_DISTANCE = 240`，0.55~1.25 倍），超过 800 格不画；
  相机背后/出界的自然被裁掉。放在 HUD 最底层（`move_child(..., 0)`），开镜时会被镜筒遮罩盖住。
* 小地图：`scripts/battle_minimap.gd`，左上角 190×190。缩略图由
  `BattleArena.map_image()` 生成：**亮色地图**（高度分色 + 西北方向 hillshade）而不是直接拿地面的
  albedo —— 那套颜色是给 3D 打光的，贴到小地图上会黑成一片、高频色斑缩到 190 像素还会变成"阴影网格"；
  掩体是烘进图里的暖灰点（3×3），
  每帧只画"几个点 + 玩家白箭头 + 边框"（实测加完这层 draw 从 ~350 涨到 ~430，帧率 138~142）。
  位置点都带深色描边（亮色地图上纯色小圆点容易糊），玩家白色箭头指向车头（`yaw` → 地图方向 `(cos, -sin)`）。
* **标记规则**（用户要求，2026-10-18 第二版）：
  - **自动标记**：敌人必须**连续**出现在某个友方载具的视野里满 `SPOT_TIME = 1 秒`
    才亮（`advance_spot()`：中间断一帧就重新计时），而且**只在 200 米以内生效**
    （`AUTO_SPOT_RANGE = 400 格`）。再远就看不见 —— 得靠手动或命中；
  - **全队共享**：任何一个友方（含 4 个人机队友）看到都算（`_team_sees()`）；
  - **手动标记**：准星附近**按 Q**（`MARK_ACTION = "mark_target"`）。实现是把每台敌车的
    **重心**投到屏幕上，取离屏幕中心最近（容差 `MANUAL_MARK_SCREEN_RADIUS = 90 px`）、
    距离 ≤ `MANUAL_MARK_RANGE = 750 米`、且在视线内的那台，立刻点亮。
    ⚠️ 视线射线必须 `exclude` 玩家自己的车（相机在车后 28 格、准星压在车顶上，
    不排除的话第一下永远打在自己车上）；瞄点用**重心**而不是"原点 + 固定高度"
    （被打成只剩核心的车很矮，抬高 1.5 格会从残骸头顶飘过去）；
  - **被友方子弹命中也会标记**：`_on_projectile_hit()` 里跨队命中后调
    `_on_vehicle_damaged(rig)`，对战模式接住 → `_mark_enemy(veh, "被友方子弹命中")`；
  - 已经标记的敌人，**全部友方都看不见之后 0.5 秒**（`SPOT_LOST_TIME`）才熄灭；
  - 视野 = 距离（自动 200 米）+ 视野锥 + 视线：玩家用**当前相机 FOV**（开镜变窄，和画面一致）
    + 4° 余量；人机车头 ±75°；视线被地形/掩体/别的车挡住不算；
  - 未标记的敌人：**头顶血条、名字、小地图红点全部不画**；友方点/血条永远可见。
  断言：`test_spotting_requires_a_continuous_second`、`test_mark_rules`、

## ESC 暂停菜单（测试场 / 人机对战共用，2026-10-18）

`scripts/pause_menu.gd`（`PauseMenu`，CanvasLayer `layer = 100`、`process_mode = ALWAYS`），
由 `TestField._build_pause_menu()` 建一份、两种模式都继承。**ESC 不再直接回主界面**：

| 按钮 | 行为 |
| --- | --- |
| 返回战斗 | `close()`：解除暂停、重新锁定鼠标 |
| 游戏设置 | 展开 `GameSettings.build_ui()` —— **和主界面「游戏设置」是同一份代码/同一份存档**，天然一致 |
| 自爆 | 二段确认（先点"自爆"再点"确认自爆"），走正常毁伤流程把玩家零件全打爆 → 对战里算你被击毁 |
| 返回主界面 | 先 `teardown_match()` 拆干净这一场，再 `change_scene_to_file(主界面)` |

**"暂停"到底怎么暂停**（踩过的坑）：

* 只设 `get_tree().paused = true` 只会停**脚本**（`_physics_process` 不跑了），
  但 3D 物理服务器还在积分 —— 车会带着速度继续滑、坠下去。
  所以 `PauseMenu.open()` 里同时 `PhysicsServer3D.set_active(false)`，恢复时再 `true`。
  实测：暂停 30 帧玩家车位移 **0.0000**。
* 引擎循环音是 `AudioStreamPlayer`，不归 pause 管 —— 开菜单时把各车的
  `stream_paused` 置 true，恢复时置回（否则菜单里一直嗡嗡响）。
* 菜单本身必须 `PROCESS_MODE_ALWAYS`，否则暂停后按钮和 ESC 全都不响应。

**返回主界面为什么要"拆一遍"**：用户报过"返回再进战斗会回到上一场、光效和队友敌人渲染两次"。
我用 `change_scene_to_file` 复现（主界面按钮进战斗 → 注入 ESC → 再进）时是干净的
（两场都是 10 台车 / 17 个转塔 / 116 个网格 / 1 个 WorldEnvironment），但为了让"下一场一定是全新一局"
变成**代码保证**而不是"应该没问题"，`TestField.teardown_match()` 会显式释放：
每台车的 chassis（连带转塔/轮胎）、射弹池、瞄准标记、相机、场地根节点，清空
`_vehicles/_wheels/_turrets/_clip_boxes/_enemies/_team_of_key`、`_spot`（子类 `_teardown_mode()`）、
`pending_vehicle`，并把 `paused` 和 `PhysicsServer3D.set_active(true)` 复位，再换场景。

## 声音：所有车都有引擎声和枪声（3D 声部，2026-10-18）

以前只有玩家车有声音（开火声走 2D 池子、引擎声只给玩家建了一个 `AudioStreamPlayer`），
队友/敌人是哑的。现在：

* **每台车一个 `AudioStreamPlayer3D`**（`veh["audio"]`，挂在底盘上）——位置自动跟着车走；
  音量仍然由"油门按住多久"驱动（人机没有存油门，用**实际速度/50** 当负载），

* **开火声**：`_play_world_sfx(muzzle_position, ...)`，32 个 3D 声部轮着用（10 台车一起开火
  也不会互相打断），位置就是**真枪口**。自爆也用同一个函数（降音高、加 6 dB）。
* **距离衰减 + 左右声道**交给 `AudioStreamPlayer3D`（`scripts/spatial_audio.gd` 只负责配置）：
  - `unit_size = 40` 格（**20 米内满音量**）；
  - `max_distance = 700` 格（**350 米外静音**）；
  - `attenuation_model = INVERSE_DISTANCE`、`panning_strength = 1.0`；
  - `doppler_tracking = DISABLED`（车战里多普勒只会让人误判谁在动）。
  听者是**当前 Camera3D**（第三人称镜头）。实测 `viewport.get_camera_3d() == _camera`。
* 为什么不用手算 pan：Godot 4 的 `AudioStreamPlayer` **没有 pan 属性**
  （`pan` 只在 AudioStreamPlayer2D/3D 上），手算就得用两个单声道声部拼左右，声部翻倍。

* 3D 定位要求素材是**单声道**：`engine_loop.wav` 是 1 声道、`machine_gun_shot.mp3` 的帧头
  channel mode = 3（mono），都能正常定位。
* 断言（`tests/test_audio.gd`）：满音量距离 40 格 / 静音距离 700 格；`configure()` 把
  `unit_size`/`max_distance`/`panning_strength`/多普勒配成上面这组；引擎音量映射单调。

## 手动摆放掩体 / 出生点：`scenes/battle_arena.tscn`（Godot 编辑器里拖，2026-10-18 第四版）

**主入口是编辑器场景**，不是文本文件了：

```
Scenes/battle_arena.tscn
 BattleArena (scripts/battle_arena.gd，@tool：编辑器里自动铺一张地面预览，owner=null 不存盘)
   ├─ Cover   ← 石头/崖壁：每个都是 nature_kit 的 .glb **实例**，用 W(移动) / R(缩放) / E(旋转) 直接改
   ├─ Decor   ← 树/灌木（不挡车，只挡视线？不，纯装饰；也不挡子弹）
   └─ Spawns  ← Team0_0…Team0_4 / Team1_0…Team1_4：Marker3D，拖位置 + 转朝向
```

* **加一块石头**：选中 `Cover` 里任意一个石头 → `Ctrl+D` 复制 → 拖到新位置、`R` 缩放；
  要换模型就在"检查器"里把它的场景换掉（或从 `assets/arena/nature_kit/` 拖一个 .glb 进 `Cover`）。
* **删掉** = 游戏里也没了；**整体挪/转/缩放 `Cover`** 也行（碰撞用的是世界 AABB）。
* **出生点**：拖 `Spawns/Team0_x` 的 Marker3D，转它改车头朝向。**`Team0_0` 就是玩家自己**，
  后面 4 个是队友，`Team1_*` 是敌人。⚠️ 不要移动/旋转 `Spawns` 节点本身（marker 用的是相对它的本地变换）。
* 保存场景（Ctrl+S）→ 进战局就按场景摆，**不用重启编辑器、不用改代码**。

**运行时怎么处理**（`BattleArena._build_props_from_scene()`）：

* 视觉：`Cover`/`Decor` 里所有 MeshInstance3D 按**网格**合批成 MultiMesh（7 个节点）——
  源节点只是编辑器里的摆放工具，运行时 `visible = false`；
* **装饰（树/灌木）全部常驻**（2026-10-18 用户要求改回）：不再按距离加载/卸载 —— 之前"300 米内才画"会在边界整批消失/出现，看着像闪一下；现在 7 个合批节点、300 个实例一直渲染，数量由 `data` 里的 `TREE_COUNT/BUSH_COUNT`（重新烘焙）或直接在 `scenes/battle_arena.tscn` 的 `Decor` 里增删节点决定。
* **MultiMesh 的物理插值必须关掉**（`RenderingServer.multimesh_set_physics_interpolated(rid, false)`，
  装饰和车体分组都要）：这两处的实例数组都会在运行时**整体重排**（装饰按距离、车体按存活零件）。
  开着插值的话，重排那一帧渲染器会把"新实例"和"上一帧同一个下标的实例"插值一遍 ——
  看到的就是**树突然挪了位置、车身突然少几个零件，一帧后又恢复正常**（用户 2026-10-18 报的闪烁）。
  车体的整体移动靠父节点（刚体）的插值，每个实例本身是静态的，不需要插值。
* 碰撞：把所有掩体的**三角形**合成一张 **trimesh**（`ConcavePolygonShape3D`，一个 `CoverBody`）—— 凹进去的地方真能塞进去、斜石头不再挡出一圈空气墙；500 米场地实测 7602 三角，物理仍稳定 120 tick/s；
* 小地图灰点：只来自**实体掩体**（`cover_points` 条数 == 掩体数，树/灌木不在里面），
  从每个掩体的包围盒中心来（米）。

**重新烘焙一版**（改了自动摆放参数、或想从零再撒一遍）：

```
godot --headless --path . --script res://tools/bake_arena_scene.gd
```

会**覆盖** `scenes/battle_arena.tscn`（500 米场地：约 115 掩体 / 300 装饰 / 10 出生点）。

**兜底顺序**：场景里 `Cover`/`Decor` 有子节点 → 用场景；没有 → 文本布局
（`data/arena/battle_layout.txt`，可选，格式见 `LAYOUT_PATH` 注释）；再没有 → 程序化自动生成。
出生点同理：Marker3D → 文本 `spawn` 行 → ±110 米自动列阵。

断言：`tests/test_battle.gd::test_manual_layout`（文本布局解析/优先级）与
`test_scene_spawn_markers`（场景 Marker 优先于文本布局）。
## 测试的统计口径（"TOTAL= / ASSERTS=" 是什么意思，2026-10-18）

`tools/run_tests.gd` 现在打印：

```
TOTAL=223 FAILED=0 ASSERTS=7641（223 个测试方法 / 7641 条断言）
```

三个词的含义：

| 说法 | 是什么 | 当前数量 |
| --- | --- | --- |
| **suite（套件）** | `tests/test_*.gd` 一个文件 | 17 个 |
| **测试方法** | 套件里一个 `func test_*` | 223 个 |
| **断言** | 代码里一次 `assert_true/eq/gt/...` 调用（一个方法里常有几十条） | 7641 条 |

`FAILED` 数的是**测试方法**（一个方法里任何一条断言挂了，这个方法就算失败；后面的断言还会被计数但不再改变结果）。

⚠️ **踩过的坑**：插件 runner 的 `_results` 是 `Array[Dictionary]` 类型属性，
`runner.set("_results", [])` 这种清空方式在类型不匹配时**不会真的清空**，于是上一版脚本把
"累计方法数"当成了总数，报出 `TOTAL=1979` —— 那个数字既不是断言数也不是套件数。
现在每个套件都新建一个 `McpTestRunner`，数字才是干净的。

**0 失败**。曾经红过的那条（`test_twin_mg_reuses_the_single_turret_geometry` 的"每发更费电"）已经清理掉了：
用户确认**只比每秒耗能**，不比每发单价 —— 双联装 rpm 900、单连装 500，每发都是 100 时，
每秒是 1500/s vs 833/s，本来就"更费"。现在那条断言比较 `energy_cost / fire_interval_seconds()`。

**只跑相关套件**（日常改代码别全跑）：

```
godot --headless --path . --script res://tools/run_tests.gd -- --suite=weapon
godot --headless --path . --script res://tools/run_tests.gd -- --suite=weapon,battle --filter=twin_mg
```

`--suite` 认 `suite_name()` 或文件名（`test_weapon.gd` → `weapon`）；`--filter` 是方法名子串。
